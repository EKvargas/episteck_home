## 4. Why the Object Storage candidate stops here

The journal entry identity is the logical `(partition, generation, revision)` slot. S-3/WS-1 requires the **store** to reject a second create for that slot. The specified candidate needs Object Lock, which requires versioning. Hetzner's unsupported conditional PUT means a `PutObject` for an occupied key cannot be relied on to return an exclusive-create conflict. Its documented behavior instead permits another version at that key. The previously accepted version may remain retained, but the logical identity is no longer single-valued through an ordinary key read/list. Client-side read-before-write cannot make this atomic across two writers. This contradicts the accepted split-brain and chain-head proof precondition.

Storage Box was evaluated as the required fallback **on documentation only**. Its ordinary writable subaccount plus periodic snapshots cannot enforce S-4 at acknowledgment time. No alternate Hetzner-documented mechanism satisfying WS-1 and WS-2 was established. Provisioning a generic Storage Box namespace would not answer the contract and was therefore stopped as well.

## 5. What experiments cannot prove alone

- WS-3 requires a provider statement that a successful append response denotes durable acceptance; one successful fresh read cannot prove survival of a provider failure.
- WS-5 requires documented authoritative read/list/absence semantics. Repeated successful list trials cannot rule out a stale or incomplete answer during a failure or concurrent write.
- WS-1 and WS-2 require store-enforced behavior for all relevant operations and credentials; a small number of rejected test calls is supporting evidence, not a replacement for the capability contract.
- WS-4 requires the actual configured credential policy plus negative tests. Separation inferred from naming, projects, or a host file layout is insufficient.

## 6. Security and operational implications

No journal credential or test data was exposed because none was created. The Object Storage limitation matters even with a Compliance-locked version: a second writer can put a new current version for an occupied revision, and a delete marker can hide a retained version from an unversioned read. A version-aware client might detect ambiguity, but the accepted architecture requires the store to reject duplicate creation; detection is not equivalent to S-3. The service must fail closed with `H(p) = UNKNOWN` where completeness or absence cannot be proven.

The Storage Box snapshot schedule leaves an interval in which an acknowledged entry can be changed before any snapshot protects it. Read-only mode removes append ability. Neither realization can be selected from this evidence, so there is no new runbook, credential escrow, lease parameter, or production deployment to operate.

## 9. Hetzner Storage Box + Borg append-only — Phase 0B

Date checked: 2026-09-26. This is a **documentation and semantics review only**. It evaluates the additional Borg mechanism, not the plain writable SFTP/subaccount/snapshot realization in §3. No Storage Box configuration, SSH key, repository, archive, or backup was created, read, or changed. Hetzner documents server-side Borg 1.1, 1.2 (default), and 1.4, and recommends selecting the remote version explicitly. This review uses Borg 1.4's official semantics; Borg 2's different archive-name model cannot be assumed available on Storage Box. [Hetzner Borg support](https://docs.hetzner.com/storage/storage-box/access/access-ssh-rsync-borg/), [Borg 1.4 create](https://borgbackup.readthedocs.io/en/stable/usage/create.html), [Borg 2 create](https://borgbackup.readthedocs.io/en/latest/usage/create.html).

### 9.1 Decisive semantics

Hetzner expressly warns that an append-only **restricted client can still delete archives logically**: they are marked deleted, and an unrestricted write/delete can later reclaim them. [Hetzner Borg support](https://docs.hetzner.com/storage/storage-box/access/access-ssh-rsync-borg/). Borg says `--append-only` prevents overwrite/deletion of committed **segment files**, but `borg delete`, `prune`, and reads remain allowed; those commands write a new transaction marking data deleted. `borg compact` does nothing in append-only mode. Physical bytes and older manifests may be recoverable by an operator before unrestricted compaction, but normal repository enumeration uses the newer logical state. [Borg append-only and transactions](https://borgbackup.readthedocs.io/en/stable/usage/notes.html), [Borg serve](https://borgbackup.readthedocs.io/en/stable/usage/serve.html), [Borg list](https://borgbackup.readthedocs.io/en/stable/usage/list.html).

That distinction is decisive. The Knowledge credential must be able to read the **authoritative accepted history during verification**. A service credential that can issue a successful logical deletion can make an accepted archive disappear from the ordinary `borg list` view, even though an operator could recover segment bytes later. An alternate verifier that reads raw Storage Box repository files through SFTP would give the service file-level mutation access; Borg warns append-only is not enforced for `rm` or other non-Borg tools. [Borg notes](https://borgbackup.readthedocs.io/en/stable/usage/notes.html). An operator recovery procedure cannot supply the automatic complete `H(p)` proof on every start and lease renewal.

AWS was researched from official documentation only. There is no AWS account, bucket, IAM role, policy, object, or live response in this evidence. ### 10.1 Conditional identity and immutability controls

AWS [conditional-write documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html) says `PutObject` with `If-None-Match: *` succeeds when the current key is absent and returns `412 Precondition Failed` when it exists. Concurrent conditional writes to the same key allow the first completed write; later writes receive `412`. A concurrent delete can instead yield `409 Conflict`. In a versioned bucket, the condition checks **only the current version**: if it is a delete marker, another conditional create can succeed. AWS [bucket-policy documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html) provides `s3:if-none-match` to require the header on general-purpose-bucket uploads. The policy must allow **only this condition**, not an `If-Match` alternative. A service-scoped explicit `Deny` when `s3:if-none-match` is absent prevents a separate identity-policy `Allow` from admitting an unconditional write. The restricted identity should use small, single-request `PutObject`; it has no need for multipart or copy. AWS notes that conditional-write policy enforcement makes `CopyObject` to that prefix fail rather than becoming an unconditioned bypass. [Policy guide](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html).

AWS [Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html) requires Versioning and protects **individual versions**. Compliance retention prevents even account root from deleting a protected version or shortening its retention during the protected period. Governance can be bypassed with `s3:BypassGovernanceRetention`, so the proposed journal uses Compliance. Object Lock by itself does **not** prevent a same-key new version or a simple `DELETE`: AWS returns success for the latter and makes a delete marker current. [Object Lock delete behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html#object-lock-delete). The Knowledge service must therefore lack `s3:DeleteObject` and `s3:DeleteObjectVersion` and must have an explicit bucket/identity denial for them. This prevents that service from creating the delete marker that would reopen the conditional-create slot. This is an **inference from the combined documented API and IAM semantics**, requiring a negative live test of the effective policy.

Set **bucket default Compliance retention** so a plain conditional `PutObject` receives protected retention. Do not grant the service `s3:PutObjectRetention` or `s3:PutObjectLegalHold`: an explicit object-level retention setting can override the bucket default, and legal hold is removable by an authorized identity. Grant read-only retention inspection if needed for acceptance verification. [Object Lock retention and permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html), [Object Lock management](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html). A retained upload needs `Content-MD5` or an SDK checksum algorithm. [PutObject API](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html).

The bucket must have **no lifecycle expiration or noncurrent-version expiration rule**: AWS says lifecycle can place delete markers over locked versions. Deny the service `s3:PutLifecycleConfiguration` and verify absence of lifecycle configuration before and during the probe. [Object Lock lifecycle interaction](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock-managing.html). Keep bucket controls, policy, Versioning, Object Lock configuration, and access-point creation outside the service identity. Administrator/root access and an administrator's ability to change future configuration or add a delete marker are **operator/account residuals**, distinct from the accepted service-credential requirement. An administrator cannot shorten an already protected Compliance version's retention, though account deletion remains an extreme residual. [Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html).

### 12.3 `H(p)` proof boundary and state mapping

The probe's head procedure required deterministic one-object-per-revision names, a complete prefix scan with every page token consumed, a contiguous verified chain, and then an exact point lookup of the next revision. A `200` next-revision result extended and re-verified the chain; a strongly consistent `404` ended the proof at that point. Any failed page, unconsumed token, ambiguous point lookup, or uncertain connection leaves `H(p) = UNKNOWN` and the partition `UNVERIFIED`. A proven revision conflict, gap, corrupt hash link or wrong epoch is `BLOCKED`. During a Forget, rejection or uncertain acceptance remains `FORGET_INCOMPLETE`; only confirmed durable journal acceptance can precede local commit. A retryable transient is retried within that fail-closed envelope. The service still needs the accepted freshness lease and epoch quarantine; this probe does not implement or replace either.

The list API is **not a scan snapshot**: an object created after a page was read may be omitted if it sorts into an already-listed range. The accepted S-6 boundary is entries acknowledged **before** a query began; strong listing covers those. For entries created while scanning, contiguous-chain verification plus exact `r+1` lookup prevents the tested stale-head conclusion. A later append can of course occur after a completed proof; the accepted lease bounds that interval. These are the stated limits of WS-5 PASS, not a claim of transactional multi-page listing.
