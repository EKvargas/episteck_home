# KAP-2 Knowledge incarnation and admission amendment

**Status:** Board recovery amendment prepared for architectural review; KAP-2 implementation and activation remain open. **Dependencies:** [runtime contract §19](KNOWLEDGE_AUTHORIZATION_PLAN_RUNTIME_CONTRACT.md), [PR #64 feasibility brief](KNOWLEDGE_KAP2_TRANSACTIONAL_WITNESS_FEASIBILITY.md) at `b00692d0fe6f08d4cbcdffd8dbab9811370dfa49`, accepted KAP-1 PR #58 and disconnected evaluator PR #60. PRs #61–63 remain GCS experiment evidence; their request-time path is rejected and is not reused here.

## Scope and terms

| Term | Exact meaning |
| --- | --- |
| Knowledge admission | A live, partition-scoped permission for the new Knowledge RT#1/RT#2 path to evaluate; it is not a grant to a Person and has no effect on existing Home APIs. |
| Incarnation | A fresh CSPRNG-generated 256-bit identifier minted after every witness gateway/database restart, replacement or uncertain recovery. Known collisions reject; uniqueness across lost history is probabilistic. `(incarnation, revision)` is the Knowledge authorization fence; revision order is meaningful only within one incarnation. |
| Reauthorization | A new affirmative Knowledge-scoped act by the authenticated, currently empowered issuer, with exact partition, target, domain, actions and dependency proof. For Person self-access, the same authenticated Person activates self-access anew. It is not copying a prior `Consent Grant`, bulk operator approval or a restored `granted_by` string. |
| Quarantine | Previous Knowledge grant/activation rows can remain as audit evidence but cannot satisfy a current-incarnation policy check. The underlying Home grant or unrelated API permission is not revoked or edited. |

The amendment does not add fields to KAP-1's v1 wire objects: `authorization_revision` remains an opaque printable string issued by Home, now binding the incarnation and local revision; `disclosure_fence` is similarly Home-issued. No consumer can infer an allow by parsing or comparing those strings. Every Home Knowledge context stores the actual incarnation separately and RT#2 compares it with a fresh admitted witness read. R13 v1 already carries `authorization_revision`; no new signed claim is added. Existing R13 `DOMAIN_READ` calls are one-use and at most 60 seconds; an already issued basis can finish a read in the trusted runtime, but an old-incarnation context cannot pass RT#2 or release a ContextBundle. A future write-capable basis or immediate domain-side basis cancellation requires separate review.

The proposed Home-owned reauthorization record is `(incarnation, partition, grantee Person, typed target, domain, exact actions, authenticated issuer Person, current issuer/dependency evidence, underlying Home grant reference when applicable, event ID)`. A separate Person self-activation record binds the same Person as authenticated actor and target. These are Knowledge admission records, not replacement ConsentGrants. The reauthorization process uses the existing trusted Frappe session→User→Person resolution and a guarded Home mutation, not an actor field supplied by the runtime or operator. A changed/revoked underlying grant or issuer dependency invalidates its Knowledge activation; the overlay never widens the underlying Home permission. The concrete private reauthorization UI/API is a later KAP-2 implementation review and does not change existing Home endpoint behavior in this amendment.

## Candidate independently enforced gate

A dedicated Home-owned gateway on the **Nuremberg host** is the only network-accessible route to a dedicated local MariaDB witness. Home/Frappe and other clients have no direct witness database, privileged Unix socket, schema DML/DDL or recovery credentials. The gateway authenticates Home's registered caller and uses separate least-privilege MariaDB procedure principals for read, mutation and recovery. This is a candidate architecture, not installed infrastructure; an operator and identities are not yet assigned.

The gateway starts in volatile `CLOSED` state **before** opening its listener. It takes one local exclusive process lock; a second instance cannot publish or serve. It pins its database connection identity and closes admission on any connection loss, process restart, database restart, lock loss or operator-declared restore. An unknown mutation acknowledgement on a continuously live witness blocks that partition as PENDING until exact-event readback resolves it; unresolved uncertainty closes admission and triggers recovery. `CLOSED` is not read from the witness database or Home, so restoring both databases with old `READY`/`COMMITTED` rows cannot admit them. Only the gateway can set its in-memory state to `REAUTH_ONLY` and then `OPEN` after the recovery sequence below. Any listener, maintenance tool, connection pool, service restart or direct SQL path that can bypass this gate is a rejection of the candidate. This boundary assumes trusted Nuremberg root/DB administration; live privileged rewrites that bypass the controlled restore procedure require a stronger independent authority and are outside this minimal candidate.

Normal RT#1 and RT#2 calls hold the guarded Home partition snapshot and make **one authenticated remote gateway read** of the current witness row in a real transaction. They require gateway `OPEN`, matching partition/incarnation/revision/authority digest, `COMMITTED`, valid current Knowledge reauthorization and current typed policy/session/target facts. Missing, PENDING, mismatched, stale, timed out or malformed results deny. The Home allow linearization point remains the current witness read while the Home lane is held. The gateway has no cached `OPEN` answer that Home may reuse. Other Home APIs continue through their existing policy paths; they never consult this Knowledge admission overlay.

The witness row stores partition, incarnation, current revision, writer and publisher epochs, `PENDING`/`COMMITTED`, event ID and canonical authority digest. The digest includes the incarnation, default-deny/current reauthorization overlay and all Knowledge-relevant policy facts under a versioned encoding. A compact unique event table provides idempotent exact-event readback. Authenticated epoch-specific `SQL SECURITY DEFINER` procedures alone may make legal transitions under row locks; the Home site and old epoch principals have no direct DML. A mutation reserves `PENDING`, commits the protected Knowledge authority change plus event/revision/digest in Home's local transaction, then publishes matching `COMMITTED`. In a gap or unknown acknowledgement, readers deny and retries compare the exact event across both stores. A timeout never aborts/reuses a reserved revision by guess. The guarded Home mutation boundary must cover every Knowledge-relevant source, including User, Person, session, grant, Circle and partition changes, while ordinary non-Knowledge Frappe operations still work. A general Home mutation may change existing Home policy as it does today; only its Knowledge projection/overlay and fence join the new boundary.

### Recovery sequence, all Knowledge reads denied until step 6

1. Gateway process/database restart, replacement, connection/lock loss or uncertainty immediately leaves the gateway `CLOSED`; network policy prevents direct witness reads. Stop or drain old Home Knowledge writers and reject old publisher epochs. A Home process that sees gateway failure denies RT#1/RT#2; an old response cannot reopen admission.
2. Operator starts a separately authenticated **recovery-only** channel. The gateway mints a new unpredictable incarnation while closed; it does not trust the restored numeric revision or `READY` flag. A failed or ambiguous incarnation write leaves `CLOSED` and uses exact-event reconciliation before another attempt.
3. Restricted witness procedures install the new incarnation, revision zero/default-deny overlay and new writer/publisher epochs. Home installs the same incarnation and quarantine marker under its guarded partition transaction. Any Home↔witness gap or delayed old writer leaves `CLOSED`; old epoch procedure calls must be rejected even if credentials remain valid.
4. Home makes all prior Knowledge context handles unusable by comparing the stored incarnation at RT#2, regardless of Redis or Home backup restore. Namespace deletion is best-effort hygiene. The runtime discards in-flight plans/content on a recovery signal or subsequent denial. Existing Home sessions and unrelated permissions stay intact.
5. The gateway reads back both stores' exact incarnation, default-deny overlay, revision, epochs and digest, verifies no unresolved PENDING event and that old privileged connections were drained. Unknown outcome, missing partition, wrong principal, witness outage or mismatch leaves `CLOSED`. It may enter `REAUTH_ONLY` for separately authenticated Knowledge reauthorization mutations; normal RT#1/RT#2 still deny.
6. After the default-deny state and direct-bypass checks are proved, the gateway enters volatile `OPEN`. Only current-incarnation reauthorization can then allow. Previous grants, Circle membership/care and Person self-access by identity equality alone remain denied until their required affirmative act. A later restart repeats the entire sequence, even after a clean shutdown.

This does not reconstruct old numeric high-water. It preserves the accepted **no automatic revival** outcome because the old incarnation is never admitted and no old grant is copied into the new overlay. If the gateway cannot independently enforce closure before any restored Home+witness pair is served, this Board amendment is insufficient and production activation must stop.

## Finite disposable integration acceptance and rejection

Use synthetic Persons, Circles, grants and contexts on a disposable Frappe site and two private MariaDB services; no production schema or data. The test run is complete only with archived per-step results and these outcomes:

1. With current `OPEN`/matching `COMMITTED`, an explicit current-incarnation grant allows; `PENDING`, witness outage, mismatch and bad digest deny at RT#1 and RT#2. Both reader-first and revocation-first schedules preserve the accepted order.
2. Kill/restart the gateway and separately restart/recreate its database while Home retains an old permissive grant: the **first** post-event RT#1/RT#2 denies before any operator action. Old Redis contexts and a restored copy deny. New incarnation differs; revision may restart at zero without old permission returning.
3. Restore both Home and witness to matching old permissive rows after a committed revocation. Direct requests still hit the default-closed gateway and deny. Reopening from restored `READY`, missing process lock, a second gateway instance, or direct DB reachability fails the test.
4. Drop acknowledgements before/after PENDING, Home commit and COMMITTED publication; retry by exact event ID. No unknown outcome authorizes or silently duplicates a grant. Delayed old writer/publisher attempts with still-valid credentials cannot commit after epoch cutover.
5. An authenticated current issuer can reauthorize exactly one Knowledge scope after current authority/dependency checks; that scope may allow in the new incarnation. Old, forged, revoked, wrong-partition, wrong-issuer, legacy and Circle-membership-only grants deny. Person self-activation requires the same authenticated Person; Circle self-access stays denied.
6. Normal Home `can_access`, ConsentGrant operations, session behavior and existing API responses for non-Knowledge workflows match the pre-gate baseline through closure, recovery and reauthorization. Generic `save/delete`, `db.set_value`, raw SQL and administrator paths cannot mutate canonical Knowledge authority outside the guarded procedure, while necessary ordinary Frappe writes continue.
7. Verify the proposed two-crossing RT#1/RT#2 path still performs one bounded witness read per Home call; capture warm/cold latency and contention distributions against the contract's complete-path p95 ≤500 ms and initial p99 ≤800 ms gates. This disposable screen cannot by itself pass KAP-10's later end-to-end live gates.

Reject or return to architecture if any old Knowledge permission/context survives recovery, the gate can be bypassed by a restored flag or direct SQL, a prior writer can complete after takeover, unrelated Home behavior changes, a needed Frappe operation is blanket-denied, or latency cannot fit the full-path gate. PR #64's local MariaDB observations are transaction evidence only; no separated-host admission or recovery proof exists yet.
