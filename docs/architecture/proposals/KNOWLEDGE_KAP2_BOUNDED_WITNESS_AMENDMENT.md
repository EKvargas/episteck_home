# KAP-2 bounded witness and writer fence — design amendment

**Status:** design candidate for architectural review; no production activation. **Base:** PR #59 at `8d9e3f904eae6015872cf4dc2178972ab4e03579`. **Measured input:** PR #61 at `74b92ca0189b0669cf852bc749c4d4f11568558d` ([sanitized evidence](https://github.com/EKvargas/episteck_home/blob/74b92ca0189b0669cf852bc749c4d4f11568558d/spike/knowledge-kap2-integration-probe/evidence/2026-10-08/LIVE_PROBE_EVIDENCE.md)). PRs #56 and #58 remain the contract dependencies; PR #60's typed evaluator remains disconnected. This amendment replaces PR #59 §4.1's per-request full scan and IAM-drain takeover, §4.5's full-scan cadence, and §5's lease-based failover sentence. The rest of PR #59's typed policy, partition binding, local MariaDB fence and guarded mutation inventory remain candidate requirements.

## Decision and measured constraint

Use a **fresh authoritative witness head**, not a signed checkpoint or MariaDB `READY` bit, as the request-time freshness source. A trusted publisher advances that head only after checking authenticated writer epoch, event, sequence, local transaction evidence and legal state transition. Each Home RT#1/RT#2 read obtains the current head under the same partition DB fence lock used by writers, verifies an independently registered signed checkpoint and at most `K` immutable journal events after it, then compares the resulting sequence/epoch/digest/event ID with current protected Home rows. A reader performs no complete historical scan. `K` is a configured hard maximum chosen by latency and storage tests, **not yet a production value**; the local model uses `K=2` to force rollover cases. A missing/invalid checkpoint, overlong suffix, newer PENDING state, restored DB, missing history or witness timeout denies the partition. Audit and restore recovery perform full historical verification out of band before admission.

PR #61's Ashburn results reject the old request path: at 64 commits, Frankfurt full-head p50/p95 was 26.425/34.735 seconds; Virginia at 68 was 9.983/11.172 seconds. They also reject IAM-only takeover: old-key signing still returned 200 for 41.92 seconds after cutover in Frankfurt and transiently in Virginia. These are observations, not propagation bounds. The governing [runtime contract §13](KNOWLEDGE_AUTHORIZATION_PLAN_RUNTIME_CONTRACT.md) keeps pre-LLM p50 ≤300 ms as an aspiration, ordinary p95 ≤500 ms as architecture target and initial p99 ≤800 ms as Gate target for the **entire** path; [KAP-10](KNOWLEDGE_AUTHORIZATION_PLAN_RUNTIME_CONTRACT.md) requires warm/cold end-to-end evidence. This design claims none of those gates.

## Candidate A: GCS generation-conditional head with a trusted publisher

Use two separate Home-owned buckets and principals per security partition or equivalently isolated namespace:

* **Immutable journal bucket:** publisher may conditionally create slots, outcomes and signed checkpoints; authorization readers may get exact named objects. A separately controlled retention policy is needed for production, but duration/lock are **not selected**. Writers have no direct object-write permission. Checkpoints are immutable, signed by a registered Home checkpoint key whose public-key history is anchored outside the restorable Home database. A checkpoint contains partition, protocol/policy version, sequence, outcome hash and generation, authority digest, writer epoch, event ID, previous checkpoint hash, signer ID and registration ID. A signature authenticates bytes; it does not prove they are the newest bytes.
* **Live head bucket:** one small current object per partition, read with a non-caching generation-aware GET. It contains partition, head generation predecessor, committed sequence and digest, latest slot/outcome hash and generation, checkpoint name/generation/hash, active writer epoch and authenticated identity mapping, plus `COMMITTED` or `PENDING` and event ID. Its publisher signature protects interpretation, while GCS's **current live generation** provides freshness under the publisher trust assumption. The head is not served through a CDN/cache. The reader rejects a missing current object, mismatched generation/bytes, wrong partition, unknown signer or unsupported version.

GCS [strong read-after-replacement consistency](https://docs.cloud.google.com/storage/docs/consistency) and [generation preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions) make a conditional replacement a candidate linearizable head operation. A stale `ifGenerationMatch` attempt returns 412. This is **not** semantic validation: GCS accepts any bytes from a principal with the necessary permission. JSON `objects.insert` overwrite needs `storage.objects.create` **and** `storage.objects.delete` for the replaced target ([Google IAM matrix, note 7](https://docs.cloud.google.com/storage/docs/access-control/iam-json)); metadata `patch`/`update` uses `storage.objects.update` and cannot be assumed to provide a safely atomic payload replacement. Head-bucket overwrite permission must be isolated from the retained journal bucket. Bucket retention that forbids replacement is incompatible with the mutable head; object versioning alone is an audit aid, not a prevention of an authorized rollback. This is a larger trusted publisher and IAM surface than PR #59's create-only journal.

The publisher is a Home-owned, separately authenticated module and the **single entry to the protected mutation procedure**; neither Frappe request code nor epoch writers receive protected-table DML, head overwrite or journal-create permission. Epoch writer identities authenticate a proposed operation to the publisher; they do not execute the procedure themselves. The publisher owns the partition lane across external PREPARE, its protected MariaDB procedure call, external outcome and head publication. It maps the *authenticated* writer principal to the active epoch from the current head, verifies the request's event/partition/slot/expected generation and a fresh guarded MariaDB transaction result, and enforces only these transitions:

`COMMITTED(n,e) → PENDING(n+1,e,event) → COMMITTED(n+1,e,event)`; or a recovery-only `PENDING → UNCERTAIN_DENY` that cannot add permission. An epoch change is its own guarded `PENDING → COMMITTED` event with `e+1` and a separately authenticated recovery/operator authorization. A pending slot blocks all authorization and next reservation. The publisher never accepts a client-provided `READY`, signature key, epoch or digest as proof. It rejects duplicate, skipped, regressing, unsupported and permissive recovery transitions. The MariaDB protected procedure remains the only canonical authority writer and binds event, epoch, sequence and resulting row digest transactionally. The publisher must read that committed event on a fresh connection before COMMIT head replacement; if its DB read is uncertain, head remains PENDING.

**Ordering and linearization.** The publisher and Home readers/writers share the protected per-partition MariaDB fence lock. The publisher conditionally creates immutable PREPARE, then CAS-replaces the head with PENDING **before** the authority transaction commits. After a proved DB commit, it conditionally creates the immutable outcome and CAS-replaces the head with COMMITTED, then reads back exact head bytes/generation before acknowledgement. The old head generation in each CAS is captured for that one attempt and never refreshed for a stale proposal. The authorization allow linearization point is the fresh current-head GET *while holding the DB read lock*, after re-reading current authority rows. A write cannot publish PENDING or commit authority until that reader releases the lock. If a writer wins the lock first, the reader sees PENDING and denies, or sees the committed new state. A restrictive mutation is effective for disclosure as soon as PENDING is visible (deny); a permissive mutation can allow only after COMMITTED. Neither a timeout nor a lost response permits an optimistic allow.

At most `K` committed slots/outcomes may follow the checkpoint named by the head. The publisher creates and readbacks a signed checkpoint of the current COMMITTED head before it permits another PREPARE that would make the suffix `K+1`; a CAS head update switches the checkpoint pointer without changing authority. If checkpoint publication or pointer CAS is uncertain, writers stop; readers still verify the previous bounded suffix or deny on an invalid pointer. The checkpoint's hash, generation, epoch, sequence and digest must match the fresh head and the verified suffix. Full-chain audit regularly verifies checkpoint derivation and reports corruption, but **a request must not substitute a cached audit result for the fresh head**.

**Takeover while old credentials work.** The authoritative epoch is the publisher-controlled current head plus the matching protected MariaDB fence row. Epoch writers have distinct authenticated principals; old signing permissions may remain usable. A delayed old submission can neither write protected rows after the DB epoch changes nor make the publisher advance a new-epoch head. If an old head CAS was already sent, it either wins before the epoch transition and must be reconciled under PENDING, or loses on generation precondition after the epoch transition. The publisher binds the old principal to its old epoch on **each** transition, including outcome publication. A delayed old writer that can still sign creates no authority, because signatures are evidence, not publication rights. Old clients have no direct head/journal write grant. If the trusted publisher process or its overwrite credential is compromised, this proof fails; that is an explicit activation risk requiring isolation, code review, key recovery and a separate test of direct-bypass denial. IAM revocation remains defense in depth, never the takeover safety condition.

**Restore and outage.** A Home DB restore behind the independently current head fails digest/sequence/epoch comparison, even if the backup's `READY` flag and a signed old checkpoint agree with each other. A head restored or maliciously rewound by the privileged publisher would defeat this witness unless a separate monotonic audit/registration anchor detects it; protect the publisher principal and prohibit ordinary head restore/repointing. Witness unavailability, unknown head outcome, missing checkpoint/suffix, invalid signature or unsupported policy version denies. Recovery performs a full scan from independently pinned genesis and immutable checkpoint history, reconciles PENDING conservatively, replays restrictive changes first, and requires authenticated reauthorization for unproved permissive grants. Session/request contexts are invalidated. No request-time full scan is allowed as a fallback.

## Candidate B: independent transactional witness

A separate Home-owned MariaDB witness on an independently operated host could hold `(partition, sequence, epoch, state, digest, checkpoint hash)` and a compact append-only event table. A definer procedure maps each authenticated writer DB principal to its stored epoch, validates the transition and performs head/event update in one transaction; readers use a current locking read. Old credentials can still connect, but the procedure rejects old principals after epoch advancement. The Home site and Frappe principals receive no witness-table DML, DDL or definer privilege. This has a smaller application-level publisher interface than GCS object CAS and can make epoch enforcement truly server-side, but requires an additional database process, replication/backup/restore operations, restricted network access, and a proved independent anti-rollback policy. Merely moving a counter to a second MariaDB does **not** solve witness rollback. Cloud SQL MySQL permits [restoring into the same instance](https://cloud.google.com/sql/docs/mysql/backup-recovery/restoring), so its database name alone is not a non-rollback identity. One possible managed alternative is Spanner, whose backup restore [creates a new database and cannot overwrite an existing one](https://docs.cloud.google.com/spanner/docs/backup/restore-backup-overview), but it has provisioned compute and new IAM/database-role costs and still needs a trusted transition service or equivalent database-enforced privilege design. None of these resources exists for Home or has been costed/measured. Candidate B is a fallback design, **not selected** by this amendment.

**Recommendation for the next experiment:** Candidate A, conditional on a separately reviewed publisher trust boundary and an immutable non-rollback audit of head transitions. It reuses the measured GCS capabilities while making writer epoch checks independent of IAM propagation. The new overwrite principal and mutable-head rollback threat are material; if direct-bypass isolation, checkpoint proof or bounded latency fails, return to Candidate B rather than relaxing freshness. This is an experiment recommendation, not production mechanism approval.

## Executable local failure model

[`spike/knowledge-kap2-bounded-witness/model.py`](../../../spike/knowledge-kap2-bounded-witness/model.py) is a deterministic synthetic state machine, not a GCS or Frappe implementation. [`test_model.py`](../../../spike/knowledge-kap2-bounded-witness/test_model.py) asserts these cases:

| Adversarial schedule | Expected result and authorization linearization |
| --- | --- |
| Valid old signed checkpoint presented after a newer head/checkpoint | Deny; fresh head pointer and suffix bound take precedence over signature. |
| PENDING published before reader lock versus reader lock first | Writer-first reader denies; reader-first allow linearizes at fresh head GET while lock held and writer waits. |
| Old writer's prepared request and signature delivered after epoch takeover | Reject at publisher and protected DB epoch check; an already-issued stale CAS gets 412. No restored allow. |
| Home restored to a snapshot before committed revocation | Deny on head/DB sequence, epoch or digest mismatch; old READY inert. |
| PREPARE or COMMIT head publication response lost | Fresh readback resolves exact matching bytes/generation and matching DB state; PENDING or unavailable readback denies. A proved matching COMMIT may authorize under a fresh reader check. |
| Witness unavailable or journal/checkpoint missing | Deny with no cached-head fallback. |

The model tests state-machine invariants and request counts only. They cannot prove GCS conditional overwrite IAM, retained-head history, publisher isolation, MariaDB transaction ordering, real cryptographic trust, operational recovery or latency.

## Next bounded live experiment — separate approval required

No project is provisioned here; PR #61's isolated project is `DELETE_REQUESTED` and billing is disabled as of this amendment's read-only check. A new cloud experiment needs explicit approval for project/billing, region and resource/cost caps. Proposed **one-region** inventory: one new isolated project, one regional head bucket without retention, one distinct regional immutable journal bucket with a separately reviewed retention setting (**no lock** in this probe), one key ring, three SOFTWARE Ed25519 CryptoKeys/versions (two epoch signers and one checkpoint signer), four service identities (old writer, new writer, publisher, read-only verifier), one existing operator, and narrow bucket/key bindings. Only the publisher has head overwrite and journal-create privileges; neither writer can call GCS. One region near Ashburn is the first latency candidate; a Frankfurt comparison or residency requirement would double regional buckets/keys/identities and requires a separately approved count. Use only synthetic data on the actual Ashburn host. Cap proposal per region: 64 authority events, 8 checkpoints at `K=8`, 160 head-overwrite attempts (128 normal PREPARE/COMMIT replacements, 8 checkpoint-pointer changes and up to 24 adversarial/retry attempts), 160 immutable creates, 4,000 GETs, 500 LISTs for recovery/audit only, and 160 sign attempts per key; **4,820 maximum planned object requests** across those categories, with a hard 5,000 emergency cutoff. Abort on any category cap. A fresh full scan is excluded from authorization requests. A project-filtered USD 5-equivalent budget alert is notification, not a cap; a precise estimate awaits region, retention and request-class review. Provision no paid resource until Erick approves the final inventory. Preserve append-only JSONL results to a verified local file after **each** step, sync sanitized checkpoints to the local worktree during the run, and emit final stdout only as a redundant copy. A lost SSH channel must leave the last verified step and counters intact. Never persist tokens/private keys. Teardown must remove objects/buckets/identities/budget, disable key versions without irreversible destruction and close only the isolated project; retain sanitized evidence.

Before any paid run, the local contract should define an internal witness-read latency budget small enough to leave room for two Home network crossings, domain work and ContextBundle under the governing whole-path p95 ≤500 ms and p99 ≤800 ms. Two previously measured Home crossings at roughly 120 ms p95 each leave roughly 260 ms of the p95 target for all Home work, domain execution and bundling; percentile arithmetic is only a planning approximation, not a pass proof. Proposed *experiment screening*, not a contract change: 100 warm and 100 cold **pairs** of fresh-head+bounded-suffix reads at 0/1/8 suffix events, report individual and paired p50/p95/p99 and exact object-request counts; flag Candidate A if the **paired witness-only** p95 exceeds 100 ms or p99 exceeds 200 ms from Ashburn. That provisional 100 ms p95 allocation leaves roughly 160 ms for other work in the 500 ms target; only KAP-10's actual whole-path warm/cold distributions can pass the gate. Exercise both lock orders, delayed old token/signature/CAS, missing checkpoint, stale signed checkpoint, restore-before-revocation, PENDING, lost acknowledgement and outage. Measure publisher write cost and recovery full-scan cost separately. Verify `storage.objects.delete` cannot reach the journal bucket and old writers cannot overwrite the head. The architect must approve publisher isolation, retention, checkpoint frequency, regional/residency choice and costed resource inventory before provisioning.
