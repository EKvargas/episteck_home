**Historical status:** design candidate for architectural review; no production activation. **Base:** PR #59 at `8d9e3f904eae6015872cf4dc2178972ab4e03579`. **Measured input:** PR #61 at `74b92ca0189b0669cf852bc749c4d4f11568558d` ([sanitized evidence](https://github.com/EKvargas/episteck_home/blob/74b92ca0189b0669cf852bc749c4d4f11568558d/spike/knowledge-kap2-integration-probe/evidence/2026-10-08/LIVE_PROBE_EVIDENCE.md)). PRs #56 and #58 remain the contract dependencies; PR #60's typed evaluator remains disconnected. This amendment replaces PR #59 §4.1's per-request full scan and IAM-drain takeover, §4.5's full-scan cadence, and §5's lease-based failover sentence. The rest of PR #59's typed policy, partition binding, local MariaDB fence and guarded mutation inventory remain candidate requirements.

## Decision and measured constraint

Use the **current witness head plus an exact immutable successor probe**, not a signed checkpoint or MariaDB `READY` bit alone, as the request-time freshness proof. A trusted publisher advances the head only after checking authenticated writer epoch, event, sequence, local transaction evidence and legal state transition. Each Home RT#1/RT#2 read obtains the current head under the same partition DB fence lock used by writers, verifies an independently registered signed checkpoint and at most `K` immutable journal events after it, compares the resulting sequence/epoch/digest/event ID with current protected Home rows, then GETs the exact immutable slot `head.sequence + 1`. A present slot, unreadable response or uncertain 404 denies; only a verified absent successor can allow. A reader performs no complete historical scan. `K` is a configured hard maximum chosen by latency and storage tests, **not yet a production value**; the local model uses `K=2` to force rollover cases. A missing/invalid checkpoint, overlong suffix, newer PENDING state, restored DB, missing history or witness timeout denies the partition. Audit and restore recovery perform full historical verification out of band before admission.

PR #61's Ashburn results reject the old request path: at 64 commits, Frankfurt full-head p50/p95 was 26.425/34.735 seconds; Virginia at 68 was 9.983/11.172 seconds. They also reject IAM-only takeover: old-key signing still returned 200 for 41.92 seconds after cutover in Frankfurt and transiently in Virginia. These are observations, not propagation bounds. The governing [runtime contract §13](KNOWLEDGE_AUTHORIZATION_PLAN_RUNTIME_CONTRACT.md) keeps pre-LLM p50 ≤300 ms as an aspiration, ordinary p95 ≤500 ms as architecture target and initial p99 ≤800 ms as Gate target for the **entire** path; [KAP-10](KNOWLEDGE_AUTHORIZATION_PLAN_RUNTIME_CONTRACT.md) requires warm/cold end-to-end evidence. This design claims none of those gates.

## Candidate A: GCS generation-conditional head with a trusted publisher

Use two separate Home-owned buckets and principals per security partition or equivalently isolated namespace:

* **Immutable journal bucket:** a dedicated append principal may conditionally create slots, outcomes and signed checkpoints; authorization readers may GET exact named objects, including the successor. No head-overwrite credential can delete or replace journal objects. The **production** safety proof requires enforced no-delete/no-overwrite retention across the recovery horizon and a pinned bucket/project incarnation; duration and lock still require separate approval. An unlocked disposable run can test protocol behavior but cannot close that production obligation. Writers have no direct object-write permission. Checkpoints are immutable, signed by a separately scoped registered Home checkpoint key whose public-key history is anchored outside the restorable Home database. A checkpoint contains partition, protocol/policy version, sequence, outcome hash and generation, authority digest, writer and publisher epochs, event ID, previous checkpoint hash, signer ID and registration ID. A signature authenticates bytes; it does not prove they are the newest bytes.
* **Live head bucket:** one small current object per partition, read with a non-caching generation-aware GET. It contains partition, head generation predecessor, committed sequence and digest, latest slot/outcome hash and generation, checkpoint name/generation/hash, active writer **and publisher** epochs and authenticated identity mapping, plus `COMMITTED` or `PENDING` and event ID. Its publisher signature protects interpretation, while GCS's current live generation orders head replacements. **The head is only a candidate for freshness until the exact `sequence + 1` journal slot is proved absent.** The head is not served through a CDN/cache. The reader rejects a missing current object, mismatched generation/bytes, wrong partition, unknown signer or unsupported version.

GCS [strong read-after-replacement consistency](https://docs.cloud.google.com/storage/docs/consistency) and [generation preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions) make a conditional replacement a candidate linearizable head operation. A stale `ifGenerationMatch` attempt returns 412. This is **not** semantic validation: GCS accepts any bytes from a principal with the necessary permission. JSON `objects.insert` overwrite needs `storage.objects.create` **and** `storage.objects.delete` for the replaced target ([Google IAM matrix, note 7](https://docs.cloud.google.com/storage/docs/access-control/iam-json)); metadata `patch`/`update` uses `storage.objects.update` and cannot be assumed to provide a safely atomic payload replacement. Head-bucket overwrite permission must be isolated from the retained journal bucket. Bucket retention that forbids replacement is incompatible with the mutable head; object versioning alone is an audit aid, not a prevention of an authorized rollback. This is a larger trusted publisher and IAM surface than PR #59's create-only journal.

The publisher is a Home-owned, separately authenticated module and the **single entry to the protected mutation procedure**; neither Frappe request code nor epoch writers receive protected-table DML, head overwrite or journal-create permission. Epoch writer identities authenticate a proposed operation to the publisher; they do not execute the procedure themselves. The publisher owns the partition lane across external PREPARE, its protected MariaDB procedure call, external outcome and head publication. It maps the *authenticated* writer principal to the active epoch from the current head, verifies the request's event/partition/slot/expected generation and a fresh guarded MariaDB transaction result, and enforces only these transitions:

`COMMITTED(n,e) → PENDING(n+1,e,event) → COMMITTED(n+1,e,event)`; or a recovery-only `PENDING → UNCERTAIN_DENY` that cannot add permission. An epoch change is its own guarded `PENDING → COMMITTED` event with `e+1` and a separately authenticated recovery/operator authorization. A pending slot blocks all authorization and next reservation. The publisher never accepts a client-provided `READY`, signature key, epoch or digest as proof. It rejects duplicate, skipped, regressing, unsupported and permissive recovery transitions. The MariaDB protected procedure remains the only canonical authority writer and binds event, epoch, sequence and resulting row digest transactionally. The publisher must read that committed event on a fresh connection before COMMIT head replacement; if its DB read is uncertain, head remains PENDING.

**Ordering and linearization.** The publisher and Home readers/writers share the protected per-partition MariaDB fence lock. The publisher conditionally creates immutable PREPARE, then CAS-replaces the head with PENDING **before** the authority transaction commits. After a proved DB commit, it conditionally creates the immutable outcome and CAS-replaces the head with COMMITTED, then reads back exact head bytes/generation before acknowledgement. The old head generation in each CAS is captured for that one attempt and never refreshed for a stale proposal. The authorization allow linearization point is the **successful exact successor 404 under the DB read lock**, after the fresh head, bounded suffix and current authority rows have been checked. A write cannot commit authority until that reader releases the lock. If a delayed external slot create arrives after the 404, it cannot represent a previously committed mutation because its protected DB commit still requires the lane; the read orders first. If a writer wins first, its immutable slot or PENDING head denies until a matching COMMIT is proved. A restrictive mutation is effective for disclosure as soon as its slot is visible (deny); a permissive mutation can allow only after COMMITTED and successor absence. Neither a timeout nor a lost response permits an optimistic allow.

At most `K` committed slots/outcomes may follow the checkpoint named by the head. The publisher creates and readbacks a signed checkpoint of the current COMMITTED head before it permits another PREPARE that would make the suffix `K+1`; a CAS head update switches the checkpoint pointer without changing authority. If checkpoint publication or pointer CAS is uncertain, writers stop; readers still verify the previous bounded suffix or deny on an invalid pointer. The checkpoint's hash, generation, epoch, sequence and digest must match the fresh head and the verified suffix. Full-chain audit regularly verifies checkpoint derivation and reports corruption, but **a request must not substitute a cached audit result for the fresh head**.

**Client-writer takeover while old credentials work.** The authoritative client-writer epoch is the current head plus matching protected MariaDB fence row. Epoch writers have distinct authenticated principals; old signing permissions may remain usable. A delayed old submission can neither write protected rows after the DB epoch changes nor make the publisher advance a new-epoch head. If an old head CAS was already sent, it either wins before the epoch transition and must be reconciled under PENDING, or loses on generation precondition after the epoch transition. The publisher binds the old principal to its old epoch on **each** transition, including outcome publication. A delayed old writer that can still sign creates no authority, because signatures are evidence, not publication rights. Old clients have no direct head/journal write grant. IAM revocation remains defense in depth, never the takeover safety condition.

### Rollback safety boundary before authorization

**Selected mechanism: exact immutable successor absence.** A fresh current head and matching Home snapshot are insufficient. For a head at sequence `n`, a reader must GET `slots/{n+1}` from the independent append-only journal under the DB read lock. All mutations and publisher-epoch transitions reserve contiguous slots before changing the head or protected DB, and neither publisher head-overwrite credential nor Home restore operator can delete/overwrite them. Therefore any newer retained authority work after `n` leaves slot `n+1` present, including PENDING work. A valid old head and valid old checkpoint plus restored permissive Home state still deny after a committed revocation because the revocation slot remains. An HTTP 404 is usable only from the pinned bucket/project incarnation, with authenticated non-cached GCS read and no prior missing/gap proof; timeout, 403, 5xx, inconsistent metadata or missing bucket denies. This adds **one exact GET per authorization**, independent of history length. Strong GCS object read/list consistency is the candidate store property; immutable retention and IAM isolation remain unproved for this new production layout.

The threat boundary includes accidental Home/head backup restore, a publisher restarting from stale local state, and misuse of a **head-only overwrite credential**: each may make the live head obsolete, but cannot erase the next immutable slot, so serving blocks synchronously. A head-only credential can still cause denial of service or a malformed future head. The journal append/checkpoint signer is separately scoped; misuse of both publication and signing privileges, journal deletion, replacement of the pinned bucket incarnation, or compromise of the trusted transition code is **outside this proof** and must be addressed by retention, credential separation, deployment pinning and operational recovery before production acceptance. An asynchronous audit cannot substitute for the exact successor GET. A transactional witness would add a second authoritative database and its own anti-rollback restore proof; the exact GET avoids that service while preserving the create-only journal property. If the journal cannot be made non-deletable through the recovery horizon, Candidate A fails and Candidate B needs review.

**Restore and outage.** A Home DB restore behind the current head fails digest/sequence/epoch comparison. A combined old Home/head restore is blocked by the retained successor slot even if both old signatures and digests match. Witness unavailability, unknown head outcome, missing checkpoint/suffix, invalid signature or unsupported policy version denies. Recovery performs a full scan from independently pinned genesis and immutable checkpoint history, reconciles PENDING conservatively, replays restrictive changes first, and requires authenticated reauthorization for unproved permissive grants. Session/request contexts are invalidated. No request-time full scan is allowed as a fallback.

### Publisher-process takeover and lock loss

Publisher process incarnation is distinct from client-writer epoch. The protected Home procedure binds each authenticated publisher principal to a monotonically journaled **publisher epoch** and checks it with the event/sequence/digest in the same transaction. A new publisher obtains the DB partition lane, fetches current head and exact successor, resolves any PENDING result conservatively, then records a publisher-epoch transition in a new immutable slot. It publishes PENDING, advances the protected DB publisher epoch, publishes matching outcome and COMMITTED head, and only then admits new work. Two processes sharing one current principal still serialize on the same DB lane. A process with an old principal may retain GCS credentials, but its protected DB commit is rejected after epoch transition; a stale in-flight head CAS uses its original generation and gets 412 after takeover. It cannot refresh that precondition and retry an old proposal.

The lane must use a dedicated live MariaDB connection and a database-enforced procedure, not a caller-set flag. On connection loss, its server-side lock and connection identity die; the process discards its event and cannot commit through a new connection without fresh epoch/head/successor validation. A delayed PREPARE object/CAS may still arrive and leave a successor or PENDING head, causing denial until reconciliation. A COMMIT CAS already sent **after a proved DB commit** may arrive after lock loss; if it wins before takeover, recovery verifies its exact event and digest. Takeover cannot pass an unresolved PENDING head. If takeover has already advanced the head, the stale CAS fails 412. A restarted publisher never trusts local pending/READY state or a remembered generation; it reconstructs from current head, successor, DB event and immutable outcome. Unknown ordering stays blocked. The local model covers these schedules, but actual MariaDB connection invalidation and direct GCS IAM bypass still need disposable integration proof.

## Candidate B: independent transactional witness

A separate Home-owned MariaDB witness on an independently operated host could hold `(partition, sequence, epoch, state, digest, checkpoint hash)` and a compact append-only event table. A definer procedure maps each authenticated writer DB principal to its stored epoch, validates the transition and performs head/event update in one transaction; readers use a current locking read. Old credentials can still connect, but the procedure rejects old principals after epoch advancement. The Home site and Frappe principals receive no witness-table DML, DDL or definer privilege. This has a smaller application-level publisher interface than GCS object CAS and can make epoch enforcement truly server-side, but requires an additional database process, replication/backup/restore operations, restricted network access, and a proved independent anti-rollback policy. Merely moving a counter to a second MariaDB does **not** solve witness rollback. Cloud SQL MySQL permits [restoring into the same instance](https://cloud.google.com/sql/docs/mysql/backup-recovery/restoring), so its database name alone is not a non-rollback identity. One possible managed alternative is Spanner, whose backup restore [creates a new database and cannot overwrite an existing one](https://docs.cloud.google.com/spanner/docs/backup/restore-backup-overview), but it has provisioned compute and new IAM/database-role costs and still needs a trusted transition service or equivalent database-enforced privilege design. None of these resources exists for Home or has been costed/measured. Candidate B is a fallback design, **not selected** by this amendment.

**Recommendation for the next experiment:** Candidate A with the **synchronous immutable successor GET** and separate head-overwrite versus journal/signer credentials. It reuses the measured GCS capability without adding an authoritative service; the retained next slot blocks stale-head authorization even when Home is restored with it. The create-only journal and trusted publisher are still material boundaries. If direct-bypass isolation, no-delete retention, checkpoint proof, publisher connection fencing or bounded latency fails, compare Candidate B rather than relaxing freshness. This is an experiment recommendation, not production mechanism approval.

## Executable local failure model

[`spike/knowledge-kap2-bounded-witness/model.py`](../../../spike/knowledge-kap2-bounded-witness/model.py) is a deterministic synthetic state machine, not a GCS or Frappe implementation. [`test_model.py`](../../../spike/knowledge-kap2-bounded-witness/test_model.py) asserts these cases:

| Adversarial schedule | Expected result and authorization linearization |
| --- | --- |
| Valid old signed checkpoint presented after a newer head/checkpoint | Deny; fresh head pointer and suffix bound take precedence over signature. |
| PENDING published before reader lock versus reader lock first | Writer-first reader denies; reader-first allow linearizes at the exact successor 404 after fresh head and DB checks while the lock is held; writer waits. |
| Old writer's prepared request and signature delivered after epoch takeover | Reject at publisher and protected DB epoch check; an already-issued stale CAS gets 412. No restored allow. |
| Home restored to a snapshot before committed revocation | Deny on head/DB sequence, epoch or digest mismatch; old READY inert. |
| Home **and** valid old head restored after committed revocation | Deny because exact immutable `old_head.sequence + 1` slot remains present; a signature and matching old digest cannot authorize. |
| PREPARE or COMMIT head publication response lost | Fresh readback resolves exact matching bytes/generation and matching DB state; PENDING or unavailable readback denies. A proved matching COMMIT may authorize under a fresh reader check. |
| Witness unavailable or journal/checkpoint missing | Deny with no cached-head fallback. |
| Two publisher processes, lock loss, delayed external CAS and stale restart | DB lane/connection fences DB commit; immutable PENDING blocks; stale CAS gets 412 after takeover; valid pre-takeover COMMIT orders before takeover and is reconciled. |

The two local models test state-machine invariants and request counts only. They cannot prove GCS conditional overwrite IAM, retained-journal durability, publisher isolation, MariaDB transaction ordering, real cryptographic trust, operational recovery or latency. [`publisher_model.py`](../../../spike/knowledge-kap2-bounded-witness/publisher_model.py) covers process schedules; [`request_ledger.py`](../../../spike/knowledge-kap2-bounded-witness/request_ledger.py) computes the proposed resource budget.

A new cloud experiment needs explicit approval for project/billing, region and resource/cost caps. Proposed **one-region us-east4** inventory, subject to residency review: one new isolated project, one regional head bucket without retention, one distinct regional journal bucket with no retention lock in this disposable probe, one key ring, three SOFTWARE Ed25519 CryptoKeys/versions (two epoch signers and one checkpoint signer), **five** service identities (old writer, new writer, head-overwrite publisher, journal/checkpoint publisher, read-only verifier), one existing operator, and narrow bucket/key bindings. Only the head identity has head create/delete/get; only the journal identity has journal create and checkpoint signing; neither writer can call GCS. The same trusted publisher module coordinates both scoped identities, so code compromise remains in the trusted computing base. A Frankfurt comparison would require separate approval and inventory. Use synthetic data only on the actual Ashburn host. No paid resource is provisioned until Erick explicitly approves the final package.
