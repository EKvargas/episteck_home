# KAP-2 Home typed policy and authorization fence — design for review

**Status:** revised draft design, 2026-10-07, after architectural disposition of PR #59 at `c5716b15e07577ba9ca54567b0087b63a4a78b9c`. No production policy, schema, journal, credential, migration, or endpoint is implemented here.

**Dependency:** [accepted Authorization Plan runtime contract](KNOWLEDGE_AUTHORIZATION_PLAN_RUNTIME_CONTRACT.md) in PR #56 (`2b1b9e5f896594027d35afe45d5fcabff70eafb7`), then KAP-1 contract/tests in PR #58 (`e5b2e4ff47245d7d1af4d74873e7eaabc57e7718`). This design branch starts at that exact PR #58 head. PR #56 and PR #58 remain unmerged; review of this document does not merge or deploy either dependency.

## 1. Decision sought and observed baseline

KAP-2 must make Home's B1 PERSON/CIRCLE decision, partition binding, and authorization revision a single enforceable policy boundary. A successful authorization cannot rely on Circle membership, care labels, a stale RT#1 allow, or a MariaDB counter restored with old grants. This document recommends a mechanism and names the architectural choices still needed before production implementation.

| Observed source | Consequence for KAP-2 |
| --- | --- |
| `apps/episteck_home/episteck_home/policy/access.py` and `policy/wrappers.py` | The pure evaluator and Frappe loader accept Person actor/subject grants. `MANAGE` implies lesser data actions in the same domain. Circle membership and care do not grant. The scalar self-access check has no resource type or partition guard. |
| `Person`, `Circle`, `Circle Membership`, `Consent Grant`, `Care Relationship`, and `Home Delegated Session` DocType JSON/controllers | No partition or authorization-fence field exists; Consent Grant has `actor_person` and `subject_person`, not a typed Circle target. ## 2. Process and typed domain model

The Home policy layer is the only authority for grants and their revision. A human-initiated grant, Circle creation/stewardship, revocation, household exit, or operator recovery enters a guarded Home mutation process. That process verifies the authenticated human/service and issuing capacity, binds one trusted partition, records the policy change and fence in one MariaDB transaction, and produces independent anti-rollback evidence before acknowledging success. Knowledge and domains consume Home decisions; they never update Home's fence.

The closed policy target is `(partition_id, resource_type, resource_id)` with `resource_type ∈ {PERSON, CIRCLE}`. Every requirement also names one domain and action. A grant has one Person grantee, one typed target, one domain, explicit actions, validity/state, and verified issuer/dependency evidence. The accepted B1 bounded typed evolution of Consent Grant is retained; no arbitrary-resource grant framework or second domain ACL is introduced.

| Rule | Required behavior |
| --- | --- |
| PERSON self-access | Only when the trusted actor Person equals the existing, partition-local PERSON target. The scalar equality shortcut is never used for CIRCLE, an unresolved reference, or an outside-partition Person. |
| PERSON grants | Existing same-domain action/MANAGE behavior remains, subject to current validity and proven subject or separately approved representative issuance. `granted_by`, System Manager status, care labels, or Circle MANAGE alone do not prove Person consent. |
| CIRCLE grants | No Circle self-access. Explicit current Circle grant or stewardship is required for Circle data actions, even with zero Person subjects. The authenticated Circle creation/stewardship process may establish initial bounded MANAGE; membership creation cannot. A steward may issue bounded ordinary Circle grants only within current MANAGE authority; dependent grants stop when that authority ends. |
| Whole operation | Evaluate every typed `(resource, domain, action)` tuple and its complete trusted target set. A PERSON subject's restrictions remain required when a Circle claim concerns them. A denied tuple denies its entire operation; no per-tuple salvage. |
| Discoverability | Nonexistent, outside-partition and undiscoverable targets produce the same non-enumerating refusal before content lookup. |

For the initial one-site/one-partition deployment, authenticated Frappe site/deployment identity is pinned outside caller input, while a guarded Home registry row binds that site and allowlisted service to one stable opaque partition. Registry changes advance the fence in the same transaction; an out-of-band deployment/configuration mismatch denies. Raw Host, headers, request body, Circle membership and model text never choose the partition. Actor Person, each typed target, grant, issuer/dependency and operation resource must carry or prove that same binding in site-local queries. Migration must inventory and attest legacy rows before stamping them; it cannot infer a partition from an ID string or silently import a row from another site. Multi-partition context switching is outside KAP-2 and continues to deny.

An additive Consent Grant migration can retain `subject_person` as the legacy PERSON reference and add `resource_type`, a CIRCLE reference, immutable partition binding and issuer/dependency evidence. Exactly one target field must be populated according to type; mixed/missing values deny. Preserve legacy grant IDs, actions, state, validity and provenance. **Unproven legacy grants are quarantined from Knowledge until authenticated reauthorization**; `granted_by` alone is not issuer proof. The existing Person API stays a compatibility adapter until an approved cutover, but it cannot be an alternate authority reader after cutover.

## 3. Mutations covered by the fence

One Home-owned per-partition fence serializes all authority-affecting writes. The protected write set includes inserts, updates and deletes, including administrative and migration paths; a generic Frappe `save`, `frappe.db.set_value`, raw SQL, or a restored snapshot must not bypass it. A multi-row business process advances the fence once for the atomic unit and retains its event ID and audit evidence.

| Mutation or process | Why it changes authorization / required atomic effect |
| --- | --- |
| Consent Grant PERSON or CIRCLE create, edit, revoke, delete, validity/action/domain/actor/target/partition/issuer/dependency change | Changes the available permission or its proof. Mutation and local fence advance commit together. No implicit reactivation of revoked legacy IDs. |
| Circle creation, dissolution, stewardship designation/recovery, stewardship grant state or validity | Establishes or removes Circle authority. Initial stewardship requires an explicit authenticated create process; dissolution invalidates Circle use and grants. |
| Circle membership join/leave/delete and household exit | Join grants nothing. Exit must invalidate that Person's Circle grants and dependent ordinary grants before it is reported complete. An out-of-process delete marks affected Circle authority unresolved and denies until reconciled; it cannot leave usable stale grants. |
| Person creation/deletion, `linked_user` binding, trusted partition binding, and User enable/disable | Changes who may act or whether a typed target belongs to the partition. User/Person mapping is also freshly rechecked at RT#2. Restoring an older mapping or enabled User must not revive access. |
| Home Delegated Session revocation or authority-bearing status change | RT#2 rechecks the live row. Revocation must order against RT#2; restore invalidates all pre-restore sessions and request contexts. Session creation grants no Person data and does not substitute for policy. |
| Machine allowlist, site-to-partition/service binding, policy semantics/version and issuer rules | Changes authority even without a grant row edit. Activation is an explicit guarded policy event; unsupported code/version or ambiguous registration denies. |
| Care Relationship label/date edit | Never grants by itself. If a separately approved representative-authority process later depends on such evidence, its issuance/revocation and dependency transition join this fence before use. No guardian inference is added by KAP-2. |

The current generic System Manager permissions and empty controllers are insufficient to prove this inventory is complete. The accepted direction is a central Home mutation service with **database-enforced coverage**. DocType hooks and a caller-set connection flag cannot enforce this: `frappe.db.set_value` and direct SQL can bypass them. The candidate is a separate protected Home authority schema and restricted SQL `EXECUTE` interface, specified in §4.3. Existing site-schema authority and Frappe core User/session mutations require a complete inventory and tested cutover; their coverage is **not proven** by the synthetic probe. Any uncovered writable authority source is an activation blocker.

## 4. Mechanisms compared and recommendation

| Mechanism | Atomic Home mutation and ordering | Restore/split-brain result | Assessment |
| --- | --- | --- | --- |
| MariaDB counter in the Home site only | Row lock and same-transaction update are feasible with the existing Frappe/MariaDB stack. | A site or host restore can roll the counter and grants back together; old revoked permission can look current. | Reject as the complete fence. Keep the counter as the **local transactional component**. |
| Redis key/request context as fence | Existing Redis supports one-use ephemeral context. | Eviction, restart and restore do not preserve a durable high-water authorization history. | Reject. Redis remains KAP-3 request-context storage only. |
| Current bench backup/restic/second DB on the same restore lineage | Can capture rows, but has no independent fact newer than an older snapshot. | A simultaneous rollback can resurrect grants undetected. | Reject as the sole witness. Continue backups for recovery payload, with consistency proven separately. |
| MariaDB transaction + separate Home-owned immutable GCS journal | Same-transaction local counter and authority rows; immutable prepare/commit evidence outside the Home restore domain. | Journal head, committed projection and writer epoch detect stale/partial restore; uncertainty blocks the partition. | **Selected candidate**; protocol and production coverage remain to be proven. |

Use a dedicated **Home-owned** append-only, hash-chained GCS journal in a separate bucket and service identity from Knowledge's journal and from Home backups. The storage pattern requires conditional create, complete strongly consistent reads/listing, locked retention and no delete/overwrite power for the Home writer. The earlier Knowledge probe does **not** prove this Home deployment or authorize provisioning. Journal entries carry minimal encrypted policy deltas and digests, never free-text reasons, credentials, session tokens or content. Home owns the logical authority, replay and keys.

The effective revision is a partition-bound `(generation, sequence, policy_digest)` proved by both a local `Home Authorization Fence` row and the independent committed journal chain. A DB row alone is never a restore certificate. Each server start is a potential restore: no persisted `READY` flag is trusted. Before serving, verify the complete journal chain/head, writer epoch, local sequence, schema/policy version and a deterministic digest of current protected authority rows. Missing, stale, partial or unverifiable evidence puts only that partition in `UNVERIFIED` or `BLOCKED`; both deny.

**Guarded mutation order:** acquire the partition write lane; prove current journal head and epoch; start a fresh MariaDB transaction and lock the protected fence row; validate issuer/old state; stage authority rows and local fence in the same transaction; compute the resulting protected-state digest; conditionally create the immutable slot (`PREPARE`); commit MariaDB; prove the event ID, sequence and after-digest persisted; conditionally create the immutable `COMMIT` outcome; read back its exact generation/bytes; only then acknowledge success and release the lane. Other decisions deny while the slot is pending. A failed prepare rolls back the DB. An uncertain DB or external outcome leaves the partition blocked until reconciliation; the caller receives no success. A committed restrictive intent is replayable after restore. An unresolved permissive intent never becomes a grant merely because it was prepared.

The external journal is not a distributed transaction pretending to be atomic. MariaDB makes the authority rows and **local** fence advance atomic; the independent prepare/commit chain and readiness rule make an incomplete cross-store outcome fail closed. A journal entry ahead of the DB after restore is evidence of possible lost authority; it is not permission to reuse the restored state. Store availability and additional write latency are the cost of accepting a mutation. No asynchronous best-effort witness may turn a revocation into a reported success.

### 4.1 Immutable journal protocol and writer epoch

The object-name grammar is `home-auth/v1/partitions/{partition_token}/slots/{sequence:020d}.json` and `home-auth/v1/partitions/{partition_token}/outcomes/{sequence:020d}.json`. `partition_token` is a Home-keyed HMAC-SHA256 of the canonical opaque partition ID, hex encoded; no caller-provided ID is accepted as a path. Sequence 0 is a fixed, externally committed genesis outcome with partition, schema, policy and initial authority digest. Each later slot contains protocol version, partition token, sequence, writer epoch, event ID, operation kind, previous outcome SHA-256 and generation, before/after protected-state digests, restrictive/permissive classification, and encrypted minimal delta. Its outcome contains the exact slot generation/hash and either `COMMIT` or a conservatively reconciled `UNCERTAIN_DENY`. Both are canonical serialized bytes, signed by the Home journal identity, and created with GCS `ifGenerationMatch=0`. Retention and IAM prohibit replacement/deletion. A received timeout is resolved by GET of the exact key and comparison of generation and bytes; mismatch blocks.

There is **no mutable authoritative head object**. A reader derives the current head from a complete, strongly consistent listing plus contiguous GET/verification of slots and outcomes from a trusted checkpoint. Sequence `n+1` may be reserved only if `n` has a valid outcome. A present slot without its outcome is `PENDING` and blocks authorization and further writes. A gap, later object beyond a gap, conflicting hash/epoch, invalid signature, or unreadable object is `BROKEN` and blocks. A cached head/checkpoint is only an optimization if it is anchored in non-rollback evidence and a fresh list proves no later slot; no such optimization is approved now. Conditional creation of the single sequence key gives at most one reserved slot and one outcome for that sequence. A second writer that loses the create must read and validate the winner, never choose another sequence. The synthetic probe exercises this property; GCS IAM/retention/list consistency remain environment proof obligations.

Each slot carries a monotonically increasing writer epoch. A takeover is itself a specially classified epoch-transition slot in the same sequence chain. Before reservation, operators must prove the old writer and its GCS identity isolated/revoked, establish an upper bound on its in-flight requests and disclosure leases plus clock margin, and resolve every pending slot conservatively. The new writer then reserves the epoch slot by conditional create and publishes its outcome after local fence/epoch commit. Old-epoch DB writes fail the protected fence procedure and old-epoch readers fail fresh journal comparison. If isolation or in-flight bound is unknown, takeover stays `BLOCKED`; key uniqueness prevents two authoritative histories but cannot by itself prevent a stale writer from occupying the next slot and causing denial of service. A forged stale slot cannot be silently skipped.

### 4.2 Partition write lane and authorization reads

The **partition write lane** spans the entire PREPARE, MariaDB commit, external outcome publication and readback interval. A dedicated Home writer process serializes by partition; a MariaDB advisory lock held on a dedicated connection across the commit is a candidate backstop, not the sole cross-restore exclusion. The protected stored procedure checks current epoch/event and locks the fence row with a fresh transaction. GCS conditional slot creation is the external collision arbiter. A lost process/connection does not hand out a new READY lease: takeover first reconciles the pending slot and fences the old epoch. All Home authority mutations, including restrictive ones, enter this lane. Restrictive mutations may be applied during recovery but are not reported complete until externally committed; permissive changes are never guessed into effect.

Every authorization reader, including future RT#1 and RT#2, must obtain a fresh journal head/status and compare it with the local event ID, sequence, epoch and deterministic protected-state digest under a current MariaDB fence read. A restored `READY` column or in-memory flag has no authority. The head check is before disclosure; if a slot is pending, the journal is unavailable, the local DB is ahead or behind, or comparison is uncertain, the whole partition denies. A reader racing a writer either orders before the writer's DB transaction under the fence lock or, after commit, sees the pending slot and denies until outcome publication. No response may be authorized using an old journal head acquired before waiting on the DB lock: recheck after the lock. RT#1 is also an authorization reader, despite issuing only a plan. RT#2 additionally uses its fresh one-use context and existing final Knowledge gate. Release the read transaction promptly; do not hold it through domain execution.

### 4.3 Database principals and guarded mutation boundary

The candidate boundary places **canonical** typed grants, target/actor bindings, issuer dependencies, machine/service registration, session revocation, policy version, event records and the partition fence in a separate `home_auth` MariaDB schema. The current Frappe site principal (actual name/privileges unverified) has no privileges on that schema, including DML, DDL or `EXECUTE` of mutating procedures. It may call a Home policy service over a separately authenticated channel and read only the service's decisions. Legacy site DocTypes are nonauthoritative projections after cutover; if any existing access API continues reading them as grants, activation is forbidden.

| Principal | Required grants and prohibition |
| --- | --- |
| Frappe site runtime (`site_runtime`, logical name) | Its existing site-schema rights only; zero `home_auth.*` rights. `save`, `delete`, `db.set_value` and raw SQL through this connection cannot touch canonical authority. Actual site DB principal and wildcard grants must be audited before implementation. |
| Home authority reader (`home_auth_reader`) | `SELECT` through approved current-state views or read procedures only; no DML/DDL, no authority-procedure `EXECUTE`. GCS read/list identity separate from writer. |
| Home mutation service (`home_auth_mutator`) | `EXECUTE` only on enumerated `SQL SECURITY DEFINER` procedures, no direct protected-table DML/DDL. It alone holds GCS conditional-create identity, never exposed to Frappe request code. Procedure validates event/epoch and performs protected rows + local fence in one transaction. |
| Procedure owner (`home_auth_owner`) | Owns protected schema/procedures; no interactive runtime login or GCS identity. Definer SQL is versioned/reviewed. |
| Migration operator (`home_auth_migrator`) | Time-bound offline DDL and exact migration procedures only, revoked after verified migration; migration emits journaled genesis/cutover events before serving. Never used by request handlers. |
| Recovery operator (`home_auth_recovery`) | Time-bound, audited recovery procedures constrained by independent journal proof; cannot mark READY by editing a row. GCS recovery/retention privileges remain separately controlled and never belong to runtime. |

The local MariaDB 10.11.13 synthetic probe confirms that a site principal with no protected-schema grants cannot insert/update/delete protected rows or update the fence via SQL, and an EXECUTE-only principal can call a definer procedure while direct DML is denied. It does **not** prove that today's Frappe deployment can run with the required site-schema privilege reductions, that core `tabUser` and session writes have been rerouted, that every authority-bearing field is inventoried, or that production MariaDB has the same privileges. Before activation, run a real Frappe integration probe for generic save/delete, `db.set_value`, raw SQL, administrator writes, migrations and all §3 mutations against the selected guard. A SQL trigger keyed to a caller-set connection variable is insufficient: callers with SQL access can set the variable. If protected-schema separation or equivalent database-enforced coverage fails that probe, return a revised boundary for architectural review.

### 4.4 Crash and recovery outcomes

| Failure point | Restrictive mutation | Permissive mutation | Reader/write-lane state |
| --- | --- | --- | --- |
| PREPARE create fails or acknowledgement is unknown | Roll back local transaction; GET exact key on unknown result. A present matching slot enters reconciliation. | Same; never grant on an unproven prepare. | Deny while slot/outcome is uncertain; no next reservation. |
| Slot exists, DB has not committed | Keep conservative denial; prove rollback or complete with a new guarded local transaction only under the same event/epoch. | Abort/deny; reauthorization may be required. | `PENDING` blocks RT#1, RT#2 and writers. |
| DB commit result uncertain | Read back exact event ID, sequence, epoch and after-digest on a fresh DB connection; if unverifiable, block and recover from journal. | Same; never infer permission from an acknowledgement timeout. | `PENDING`/`UNVERIFIED`; no success to caller. |
| DB committed, external COMMIT absent or create failed | Recover the restrictive state and publish only after DB proof; otherwise keep denied. | No use until exact DB proof and matching COMMIT; unresolved result is denied, with no automatic re-grant. | Commit-gap readers deny even if a restored READY flag says true. |
| COMMIT creation acknowledgement lost | GET exact outcome key, generation and bytes; matching committed record may be acknowledged after DB comparison. | Same, without duplicate outcome creation. | Deny until readback verifies both stores. |
| Restore predates a committed revocation | Replay committed restrictive event before any READY transition. | Older local grants remain quarantined; permissive replay needs committed proof and current issuer authority. | Restored READY is ignored; mismatch denies. |
| Writer takeover or stale old writer | Isolate old writer, reconcile pending restrictive event, then journal epoch transition. | Do not accept an old-epoch grant; require current authority/reauthorization. | Deny throughout takeover and any unknown in-flight interval. |

### 4.5 Check cadence, outage and latency budget

Until a measured, reviewed optimization exists, verify current journal status on **every** RT#1 and RT#2 call, every mutation before reservation and after publication, every process startup/restart, every recovery action and every writer takeover. A local cached READY value, Redis context or restored database flag never replaces the external check. A GCS read/list/authentication outage, truncated chain or timeout denies Knowledge authorization for that partition; mutations return an indeterminate failure and await reconciliation. This is an availability tradeoff accepted for the candidate, not an achieved live service level. Baseline cost includes at least one external authoritative head discovery per authorization read and conditional slot plus outcome creates and readback per mutation, in addition to the MariaDB lock/transaction. The synthetic in-memory timings say nothing about Ashburn↔GCS latency, GCS quota, Frappe pool impact or the open Knowledge latency gates. Measure those in an isolated environment before approving production activation; do not claim KAP-10 gates satisfied.

## 5. Current evaluation and revocation order

RT#1 and future RT#2 use a dedicated current-read evaluation path, not `check_access_many` loops or cached `can_access` outcomes. RT#2 atomically consumes the KAP-3 Home context, then opens a fresh Home evaluation transaction, locks the partition fence row, verifies the Home journal readiness/epoch, and re-reads authenticated machine registration, retained session/User→Person binding, typed targets, issuer dependencies and grants from current committed state. It decides the complete contributor set under that lock and returns one disclosure fence. The auth hook's earlier identity lookup is not a substitute for this fresh read. A malformed, missing, expired or indeterminate fact withholds the whole disclosure.

Every relevant writer must acquire the same partition lock before changing authority. A revocation committed before RT#2 acquires the lock is visible and denies. If RT#2 acquires it first, the revocation waits and orders after that disclosure point; the runtime must apply the separate Knowledge final gate and release immediately, as the accepted contract requires. No `REPEATABLE READ` snapshot established before the lock may be reused: use a proven fresh transaction/current locking reads (or an explicitly tested equivalent). An external writer epoch change cannot coexist with a valid old serving lease; failover quarantines the old epoch until its maximum lease and in-flight disclosure window expire. Until that proof exists, a fresh authoritative journal-head check is required for each RT#2 and uncertainty denies. The latency impact joins the still-open KAP-10 measurement gate.

## 6. Restore, migration, deployment and rollback

**Restore admission.** Stop Home authorization serving, invalidate Redis plan contexts, advance an independently recorded Home session epoch and reject all delegated sessions from the restored epoch, then restore a transaction-consistent Home site backup into quarantine. Verify the independent Home journal from genesis/current checkpoint and epoch; compare its committed projection and digest with the local fence and authority rows. Equal values alone are insufficient if the row set, schema or policy digest differs. If the backup is behind, replay committed restrictive changes first; permissive changes require their committed proof and current issuer validation, otherwise explicit reauthorization. An unresolved prepare, missing journal object, wrong generation, stale epoch, unsupported policy code or uncertain backup consistency leaves the partition BLOCKED. Never accept an operator assertion that no revocation occurred as proof. Resume only after a new independently recorded recovery event and fresh consistency verification. A site/host restore cannot restore or delete the separate Home journal.

**Migration/cutover.** Ship additive schema and disabled policy code through the GitHub PR → `main` → deploy job path. Home has no post-deploy migration hook, so a separately approved maintenance window must run and verify `bench --site home.episteck.com migrate`; the deploy job can have recorded the new SHA even if a hook fails or migration has not run. Inventory and back up existing Person/Circle/grant/User/session rows; audit and stamp the one trusted partition; preserve grant IDs/state/provenance; quarantine mixed targets and unproven issuer history. Establish an externally committed genesis digest, install and probe database write guards, then enable the typed evaluator only when every partition and code/schema version is READY. Legacy business APIs remain governed by their existing contracts until an explicit cutover; no Knowledge endpoint is enabled by this design PR.

**Rollback/recovery.** Disable the new Knowledge authorization path and withhold disclosure if code, schema, journal or guard versions differ. Do not drop the journal, fence, triggers or high-water evidence and do not restore an older grant table as a rollback. A code rollback that cannot enforce the current journal/policy version keeps affected authorization unavailable. Reconcile a pending or stale partition through a protected Home operator procedure, recording restrictive outcomes and requiring new authenticated consent for uncertain permissive grants. Provisioning, migrations, service restarts and production data changes require separate authorization after architectural review.

## 8. Disposition, probe evidence and decisions still needed

Architectural disposition accepted the MariaDB local transaction fence, selected separate Home-owned GCS as the **candidate** independent witness pending protocol proof, accepted quarantine of unproven legacy grants from Knowledge until authenticated reauthorization, and required a central mutation boundary with database-enforced coverage. Trigger enforcement is not proven. This revision specifies an immutable-key/CAS protocol and the restricted-schema candidate; it does not claim either is production-proven.

`spike/knowledge-kap2-fence-probe/probe_protocol.py` is a disposable in-memory synthetic model. It passed six cases: DB commit-gap denial, competing slot writers, restore before revocation, uncertain commit/lost acknowledgement, writer takeover and journal outage. `probe_db.py` started a socket-only private MariaDB 10.11.13 instance with synthetic rows, then passed restricted-principal insert/update/delete/SQL bypass denials, an EXECUTE-only definer-procedure transaction, a current reader waiting for revocation, and a concurrent bypass denial. Run both with `python3 spike/knowledge-kap2-fence-probe/probe_protocol.py` and `python3 spike/knowledge-kap2-fence-probe/probe_db.py` in WSL Ubuntu. Both scripts exit nonzero on failure and remove only their own temporary state. These probes test the stated invariants; they do not test real GCS conditional requests or live Home/Frappe call paths.

Ashburn read-only SSH was unreachable via documented Tailscale and public endpoints. Thus the deployed MariaDB version/principals/grants, Frappe write paths, backup consistency, GCS Home bucket capability/retention/IAM, network/latency and live revocation ordering remain **missing evidence**. Production schema, credentials, migration, restart and deployment are out of scope here.

Before production implementation approval, the architect must decide: (1) whether this immutable per-sequence journal and per-request external check meet the required availability/latency tradeoff after a real GCS protocol and latency probe; (2) whether the separate protected schema and service/procedure boundary is acceptable once a Frappe integration probe shows complete coverage of `tabUser`, sessions, grant/target writes and administrator/migration paths; (3) the Home GCS region, retention period, key recovery and writer takeover isolation/in-flight bound. **Recommend retaining fail-closed activation gates and withholding production fence/schema work until these proofs are reviewed.** KAP-3 and both RT endpoints remain unimplemented.
