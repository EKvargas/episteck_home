## 3. Settings and single-lane invariant

The disposable database returned these settings after creation and reopen:

```json
{
  "journal_mode": "wal",
  "synchronous": 2,
  "wal_autocheckpoint": 1000,
  "busy_timeout": 5000,
  "foreign_keys": 1
}
```

SQLite value `2` is `FULL`. WAL persisted across reopen. A deliberately incorrect connection with `foreign_keys=OFF` was classified `NOT READY`; it was not silently repaired by the readiness check.

The harness created exactly one writable connection inside a one-worker serialized `WriterLane`. Every mutation used `BEGIN IMMEDIATE`; foreground writes, cleanup writes, automatic checkpoints, and explicit PASSIVE/RESTART/TRUNCATE checkpoints used that lane. Read and Online Backup API source connections opened in read-only mode with `query_only=ON`. The Online Backup destination was a separate private staging database. Negative tests for both an external writer and an external checkpointer were rejected with `PermissionError: NOT READY: writes/checkpoints are accepted only by WriterLane`. The independent busy-timeout fault exercise used its own disposable lock-probe DB, leaving the one-lane validation DB topology intact.

**Harness result:** single-writer/checkpointer enforcement `PASS`; WAL-reset-risk topology gate `PASS` for the tested harness topology. This verifies the lane abstraction and the paths exercised here. It does not prove that a future service account, systemd job, administrator, or unrelated process could not bypass the lane by opening the host file directly; production file ownership and operational tooling must enforce that boundary.

## 4. FULL commit latency

All values are Nuremberg host measurements in milliseconds, 1,000 acknowledged transactions per class, after 100 warm-up transactions. Transactions used `BEGIN IMMEDIATE`, mutation, and `COMMIT` with `synchronous=FULL`.

| Write class | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|
| Small ordinary write | 0.053 | 0.094 | 0.170 | 0.272 |
| Suppression/control-register sized write | 0.624 | 1.532 | 2.161 | 6.798 |
| Cleanup/evidence write (10 rows) | 0.742 | 1.113 | 1.406 | 4.311 |

These measurements do not include a production GCS journal append, Home crossing, domain work, or real erasure evidence processing. The values are not a direct warm/cold end-to-end latency result.

## 5. P13 write / cleanup contention

The adapted corrected P13 method used a 5,000-row synthetic local corpus, 200 warm-up operations, 500 samples per run, and alternating order `baseline / cleanup-active / cleanup-active / baseline`. The cleanup worker committed bounded batches through the same serialized writer lane. Reported percentiles aggregate 1,000 observations per condition. Reads used a separate read-only connection. Foreground writes measured queue wait plus FULL commit latency.

| Operation / condition | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|
| Read, baseline | 1.080 | 1.160 | 1.474 | 2.049 |
| Read, cleanup active | 1.441 | 1.682 | 2.027 | 2.144 |
| Write, baseline | 0.559 | 0.744 | 1.094 | 3.053 |
| Write, cleanup active | 0.783 | 1.595 | 2.622 | 8.044 |

| P13 signals | Result |
|---|---:|
| SQLITE_BUSY | 0 |
| Timeout | 0 |
| Other errors | 0 |
| Transaction retries | 0 (none implemented) |
| Cleanup batches during active read runs | 312 and 328 |

Cleanup-active p95 was 0.521 ms higher for reads and 0.852 ms higher for writes in this run. The run order reduced the prior warm-up/order confound. This is a harness adaptation of the accepted P13 contention shape using the required one-lane production topology; it is not a rerun of all Technology Gate P13 authorization scenarios or a result from the full original authorization schema.

## 6. Checkpoint behavior

| Exercise | Result |
|---|---|
| Automatic 1,000-page checkpoint window | 1,100 FULL commits; commit latency (including any auto checkpoint) p50 0.708 ms / p95 0.956 / p99 1.220 / max 8.251. WAL file remained at 5,562,032 bytes before and after because the file already had that high-water allocation. A subsequent serialized PASSIVE observation took 3.868 ms and returned `[busy=0, log=403, checkpointed=403]`. |
| Long reader / WAL retention | With a read transaction held, PASSIVE returned `[0,447,0]`: 447 frames were logged and none checkpointed. The WAL file byte length did not increase because its existing allocation was already larger; logical uncheckpointed frame growth is the relevant evidence here. |
| Manual RESTART with reader held | 5,008.1 ms; returned `[1,447,0]` after the configured busy wait. |
| RESTART after reader release | Returned `[0,447,447]`; all logged frames checkpointed. |
| Planned TRUNCATE | 3.08 ms; returned `[0,0,0]`; WAL size became 0 bytes. |
| Commit acknowledgement | Writes were acknowledged on successful COMMIT without waiting for a later manual checkpoint. Checkpoint work and all manual checkpoints ran on the serialized lane. |

Automatic checkpoint work is included in commit latency because Python’s stdlib interface does not expose a separate callback duration for the automatic PASSIVE checkpoint. No separate claim is made that every automatic checkpoint ran at exactly page 1,000.

## 7. Process-crash recovery

Each scenario was followed by `PRAGMA integrity_check` (`ok`) and `PRAGMA foreign_key_check` (zero rows). The tests used disposable data only and did not delete WAL files.

| Scenario | Observed state |
|---|---|
| Process exit before COMMIT | Transaction absent; integrity passed. |
| Process exit after successful COMMIT | Transaction present; integrity passed. |
| Process exit with non-empty WAL | Committed transaction present; WAL observed at 28,872 bytes; integrity passed. |
| SIGKILL during blocked RESTART checkpoint | Marker confirmed checkpoint entry; process exited `-9`; committed transaction present; integrity passed. |

These are process-crash tests. They do not substitute for kernel panic, sudden power-loss, or physical device-flush validation.

## 8. Synthetic journal-first L/H recovery and restore drill

The harness used deterministic synthetic hash-chained controls bound to generation, epoch, partition, and sequence. It did not contact GCP/GCS. The completed disposable SQLite artifact was copied into quarantine. Before considering admission, it checked the artifact SHA-256, `integrity_check`, `foreign_key_check`, schema identity, local `L(p)`, and durability configuration.

| Case | Observed classification |
|---|---|
| `L = H` with valid fixture | `READY_CANDIDATE` after verification |
| `L < H` | `RECONCILING`; replayed two controls in one durable local transaction; materialized outcome `suppressed`; resulting `L = H`, eligible for later READY checks |
| `L > H` | `BLOCKED` |
| H unknown / journal unavailable | `UNVERIFIED` |
| Gap, bad hash, corrupt journal, wrong generation/epoch/partition | `BLOCKED` |
| Unreconstructable permissive state | `BLOCKED` |

Restore verification took 28.4 ms; the two-entry `L < H` replay took 5.9 ms on this small synthetic database. The artifact initially reported `journal_mode=DELETE`, which the startup check classified `NOT READY`. The quarantine procedure then explicitly established WAL and read back all required settings before it returned a READY candidate. This explicit quarantine configuration was observable and separate from serving.

## 9. Online Backup API and publication

`sqlite3.Connection.backup()` ran from a read-only source connection while all live source writes continued through the serialized lane. It copied into a private staging DB. The artifact was switched to `DELETE` journal mode while still private, then closed, checked, hashed, and given a manifest before publication. The live source had `-wal` and `-shm`; neither sidecar existed beside the completed destination. The completed destination contained the committed snapshot, passed `integrity_check`, had zero foreign-key violations, schema `user_version=0`, and recorded `L(p0)=8261` for this run.

## 10. SQLITE_FULL, I/O error, and busy timeout

| Fault | Injection and result |
|---|---|
| `SQLITE_FULL` | Database-local `max_page_count` ceiling caused SQLite’s `database or disk is full`; transaction was not acknowledged; zero attempted rows were visible; integrity remained `ok`, foreign-key violations 0. Host filesystem was not filled. |
| `SQLITE_IOERR` | Deterministic adapter raised a disk-I/O error before COMMIT; transaction rolled back and row was absent. This validates fail-closed adapter behavior, not an actual SQLite VFS `SQLITE_IOERR`. |
| Busy timeout | A test-only lock holder on a separate disposable lock-probe DB caused `BEGIN IMMEDIATE` to time out using `busy_timeout=5000`; operation was not acknowledged after 5,008.0 ms. No partial transaction was exposed. |

## 11. RPO and Technology Gate composition

Daily backup plus a local persistent disk does **not** provide zero-RPO for ordinary non-journaled data after total host/volume loss. The GCS control journal protects anti-resurrection control freshness; it does not recreate ordinary payload. SQLite/restic backup recovers ordinary data to the backup consistency point, with a non-zero loss window for later ordinary writes.

Changing `NORMAL` to `FULL` materially affects the P13 foreground write/cleanup path and its commit tails. P13 cleanup-active read p95 was also measured with concurrent FULL commits, so this path is relevant to reader-contention composition. The local p95 deltas in this synthetic harness are not interchangeable with the original §27.2.1 C-small/C-medium metadata/content measurements; therefore this report does not recompute or amend those composed figures. Direct warm/cold end-to-end latency and real R14/domain measurements remain open and are not claimed closed.

The Technology Gate selection status is unchanged. Pre-runtime obligation #1 remains open. B1–B6, the SQLite/GCS selection, production GCS provisioning status, and all unrelated gate dispositions are unchanged.

## 12. Remaining unknowns and disposition

- No power interruption, kernel crash, actual host-loss, or storage-controller flush test was performed. The ext4/local block path was observed, but physical persistence and truthful flush behavior are not empirically established.
- No production runtime exists to verify its process boundary, systemd jobs, admin tooling, ownership, or filesystem permissions. The one-lane invariant passed in the harness; production integration still needs enforcement evidence.
- `SQLITE_IOERR` was injected before commit at the adapter boundary; a real VFS I/O fault path remains untested.
- No real restic upload, repository check, encrypted restore, or off-host recovery was performed.
- Journal reconciliation used synthetic fixtures, not a live service or a GCS capability. No GCS was contacted, consistent with the closed physical GCS gate.
- The P13 rerun is a focused local contention harness adaptation; it does not replace the full authorization corpus or Technology Gate end-to-end suite.
- Direct warm/cold end-to-end latency and real R14/domain measurements remain separate open obligations.

**Recommendation for obligation #1: REMAIN OPEN.** The pinned-runtime Nuremberg measurements support the proposed WAL + FULL + one-lane + Online Backup API architecture and are ready for Board review. The listed power-loss, production-lane, I/O, and restic/restore unknowns prevent closure on this evidence alone.
