**Board follow-up:** The Board selected the fresh-incarnation/quarantine contract amendment described in [§19](KNOWLEDGE_AUTHORIZATION_PLAN_RUNTIME_CONTRACT.md) and the [admission amendment](KNOWLEDGE_KAP2_INCARNATION_ADMISSION_AMENDMENT.md). PR #63's live Ashburn screen measured paired witness-only p95 of 279/311 ms (warm/cold) with suffix 0 and 1,335/1,833 ms with suffix 8, plus a real 429 on a head replacement. These are sufficient adverse results for the architect's rejection; no further optimization experiment is proposed.

## Decision and actual boundary

**Recommendation for integration testing:** a Home-owned witness service with a dedicated MariaDB/InnoDB instance on the existing Nuremberg VPS (`ubuntu-4gb-nbg1-1`), reachable from Ashburn Home (`ubuntu-4gb-ash-1`) only over the existing Tailscale mesh. **No witness operator is appointed.** Erick must assign an accountable infrastructure operator and backup delegate, separate from the Home Frappe application owner and unprivileged `home-agent`, before installation. The application service would use authenticated, least-privilege database principals; infrastructure/root and recovery principals must not be routine serving credentials. The exact owner assignment, service account, TLS identity, firewall, backup/restore runbook, and monitoring do **not** yet exist and need review. A separate schema or database on Ashburn is not an independent restore boundary.

Read-only inspection on 2026-10-09 found MariaDB 10.11.14 active on Ashburn, but no `mariadbd` binary or active MariaDB unit on Nuremberg. Nuremberg has 3.8 GiB RAM, about 2.1 GiB available and 52 GiB free disk; sharing this node with its existing agents/services creates a resource and operator failure domain. Its daily restic job protects Nutrition SQLite and Mealie data on a Hetzner Storage Box; the recorded backup inventory does not include a Home witness. That Storage Box is a backup destination, **not** a proved immutable high-water authority. Node separation would let a live witness detect an older Home restore. It does not by itself prevent both stores from being restored to matching obsolete states.

The governing [runtime contract §15 and Board decision 2](KNOWLEDGE_AUTHORIZATION_PLAN_RUNTIME_CONTRACT.md) requires the Home authorization revision to advance atomically with relevant authority mutations, never revive revoked permission after restore, and make uncertain ordering deny. The proposed two-store protocol therefore treats any gap as unavailable, not as permission to reuse a previous COMMITTED row. The current infrastructure **cannot yet satisfy the witness-restore part** of that guarantee. The existing [Knowledge restore-freshness mechanism](KNOWLEDGE_RESTORE_FRESHNESS.md) protects Knowledge-owned control state; it is not a Home authorization witness.

The candidate's ordinary threat boundary assumes the Nuremberg OS, MariaDB administrator and witness service operator are trusted; Home/Frappe, old writers and API callers are not privileged to edit witness tables. An accidental operator restore is explicitly in scope and must trigger quarantine before serving. A malicious or careless witness root administrator who rewrites live rows while keeping the admission service alive cannot be detected from those same rows; preserving safety against that action requires independent non-rollback evidence or a stronger operator boundary. The integration gate must prove that normal restore tooling cannot bypass the service shutdown/admission lock.

## Minimal protocol to test

One row per trusted partition in the witness contains `(partition, incarnation, revision, writer_epoch, publisher_epoch, state, event_id, authority_digest)`. `state` is `PENDING` or `COMMITTED`. A compact event table has a unique `(partition, event_id)` and `(partition, revision)` so retries can retrieve the exact outcome. The authority digest covers canonical relevant grants, typed policy, actor/target partition binding and the mutation event under a versioned encoding; the Home mutation transaction stores the same event/revision/digest. The complete field inventory remains a KAP-2 integration proof, especially User disablement, Person relinking, session revocation, grant/target changes, Circle exit and every legacy writable source. A digest is a comparison of state, not independent freshness evidence.

Only epoch-specific authenticated writer/publisher principals can `EXECUTE` narrow `SQL SECURITY DEFINER` procedures. They have no direct table DML, DDL, `ALTER ROUTINE`, `GRANT OPTION`, or recovery privilege. Reader principals can invoke a bounded current-read procedure only. A separate offline operator/recovery principal may change schema or restore data only while serving is externally quarantined; it is absent from Home/Frappe. Each procedure locks the partition row, checks actual granted entry point, current epoch, event ID, expected revision/digest and legal transition, then changes the row and event in one InnoDB transaction. A caller-set flag, asserted epoch, or signature alone cannot authorize a transition. Obsolete principals may still authenticate but their old procedure fails after an epoch change. Database account/role and network isolation, all Frappe mutation paths, and privileged connection cutover remain unproved for this witness.

For a mutation, the guarded Home partition lane obtains the current witness state, reserves revision `n+1` as `PENDING` with a stable event ID, commits the protected Home mutation and its event/revision/digest in the local MariaDB transaction, then publishes the matching witness `COMMITTED` outcome. There is no atomic transaction across the two hosts. A restrictive mutation is not reported complete while the witness remains PENDING; a permissive mutation is never authorized during that gap. An unknown PREPARE, Home commit, or COMMIT result is read back by event ID under both partition locks. Exact duplicates return the recorded result; conflicting reuse is rejected. An unresolved event remains PENDING and blocks authorization. Do not abort/reuse a reserved revision merely because a client timed out. Publication acknowledgement is not the authorization linearization point.

An RT#1 or RT#2 reader locks a **current** Home partition snapshot in the local transaction, makes one authenticated locking read of the witness head (inside a witness transaction; `FOR UPDATE` with autocommit alone is ineffective), and allows only matching incarnation, revision, digest and `COMMITTED` state plus the independently fresh session/policy checks. It holds the Home lane until that decision is made. A witness PENDING state, mismatch, missing row, timeout, inability to authenticate, or unknown result denies. The allow linearization point is the witness read while the Home lane remains locked: if the reader wins, a later Home revocation commit waits; if the revocation writer wins, the reader waits and sees either PENDING or the revoked Home state. Witness COMMIT occurs only after the Home transaction has committed. This ordering is a candidate to verify through actual Frappe controller paths, not an established production property. MariaDB documents that `FOR UPDATE` requires a transaction ([locking read](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update)); definer privileges must be constrained ([GRANT](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant)).

Home restored behind a live witness produces revision/digest mismatch and denies. Witness restart, restore, replacement, lost recovery evidence, or unverified backup provenance must set the **serving admission state outside the restorable witness tables** to quarantine before any reader can connect; a restored `COMMITTED`/`READY` row never admits traffic. Under the Board follow-up, re-admission uses a fresh incarnation and default-deny Knowledge overlay, then authenticated reauthorization; it does **not** assert that an older backup contains the latest acknowledged revocation. A database backup or binlog replay can recover data operationally but cannot alone prove it contains that revocation ([MariaDB point-in-time recovery](https://mariadb.com/docs/server/server-usage/backup-and-restore/mariadb-backup/point-in-time-recovery-pitr-mariadb-backup)). A live process must reject a database incarnation change or lost connection rather than silently reconnecting to an older store. Full audit, signing/archive verification and backup restoration stay outside ordinary authorization reads because old Knowledge permissions remain quarantined; asynchronous audit cannot reopen admission.

### Recovery alternatives considered before the Board amendment

To retain the accepted literal rollback-safe revision and restoration guarantee while preserving existing grants, add independently operated, non-rollback evidence of every acknowledged witness commit (including revocations), durable before acknowledgement, plus a recovery gate that verifies it before serving. That is substantial new infrastructure and operations beyond the current Nuremberg host/restic setup, even if ordinary reads remain one witness transaction. This brief does not select a storage product or build that fallback.

The Board selected the smaller Knowledge-scoped contract change: **after any witness restart/replacement or uncertain restore, quarantine every prior Knowledge permission and invalidate all previous Knowledge contexts; create a new disjoint authorization incarnation and permit only Knowledge scopes authenticated and reauthorized after recovery.** Unrelated Home grants and existing APIs are unaffected. This accepts loss of continuity of existing Knowledge permission instead of an always monotonic recoverable numeric revision, while retaining the invariant that revoked Knowledge permission cannot revive. KAP-2 remains open and no production witness should be activated.

## Local evidence and bounded cost

Run `wsl -d Ubuntu -- python3 /mnt/c/AIProjects/episteck-delivery-workspace/.worktrees/knowledge-kap2-transactional/spike/knowledge-kap2-transactional-witness/probe.py`. On disposable socket-only MariaDB in Ubuntu, seven synthetic observations passed: direct writer DML and cross-epoch procedure execution denied; PENDING was visible during the Home commit gap; matching COMMIT and duplicate rejection worked; a Home-only restore mismatched the witness; the old epoch procedure failed after takeover; combined Home/witness rollback produced matching obsolete rows. The last case is a **counterexample**, not a pass for restore safety. The existing `spike/knowledge-kap2-fence-probe/probe_db.py` also passed its protected DML and reader-waits-for-revocation checks on the same local environment. These probes use private local schemas, not the actual separated hosts, authenticated network transport, Frappe controllers or production data. They do not establish witness restart admission, timeout recovery, crash durability or latency.

The normal authorization budget is **one local Home partition locking read/transaction and one remote witness current-row locking read/transaction**, with no journal GET/LIST, historical scan or signature verification in the request path. Each mutation needs at least two witness transitions (PENDING and COMMITTED), one Home transaction and exact-event readbacks only on uncertainty. A full RT#1/RT#2 retrieval involves two separate witness reads. Cross-region round-trip latency, connection reuse, lock contention and whole-path p50/p95/p99 remain unmeasured; the accepted contract's ordinary whole-path p95 target is 500 ms and initial p99 target 800 ms. No latency gate is claimed.

## Remaining proof, effort, and finite acceptance gate

Rough engineering ranges, **not commitments**: witness schema/procedures and privilege proof 3–6 days; guarded Home/Frappe mutation inventory and cutover 5–10 days; independently enforced admission and fresh-incarnation recovery integration 5–15+ days; operations/backup/runbook and alerting 3–6 days; race/fault/latency validation 3–6 days. The default-closed boundary and mutation coverage dominate uncertainty. Existing Nuremberg capacity and ownership need an operator decision before these estimates become deployable.

One disposable integration cycle should pass all of the following before production design approval: (1) exact principal/privilege inventory and denied direct SQL, `save/delete`, `db.set_value`, administrator and legacy paths while ordinary Frappe operations still work; (2) both Home/witness lock orders and current COMMITTED/PENDING/restore truth table under actual controller paths; (3) prepare/Home-commit/COMMIT crashes, unknown acknowledgement, retry and publisher takeover with old credentials still valid; (4) Home-only restore denial and combined restore/replacement **quarantine before first read**, a fresh incarnation and authenticated Knowledge reauthorization without changing unrelated Home results; (5) witness outage, connection loss and stale reader isolation; (6) Ashburn↔Nuremberg warm/cold RT#1/RT#2 and complete KAP-10 path measurements, including contention and failures. Archive synthetic per-step results continuously. Reject the candidate if any old principal can mutate current authority, a generic path bypasses the boundary, any uncertain/rollback state allows, witness restore can serve before proof, normal operations cannot proceed, or the full-path latency gate cannot be met. No fixed IAM wait, cached READY bit, or matching restored rows can substitute for these proofs.
