# Knowledge pre-runtime obligation #1 — production SQLite durability

Status: PROPOSED FOR ARCHITECTURE BOARD REVIEW. Obligation #1 remains OPEN pending the required host validation. No Knowledge runtime or production GCS is authorized or provisioned.

Date: 2026-09-27

Decision scope: SQLite durability, consistent off-host backup, and restore admission for the already selected SQLite 3.41.2 via Python 3.11.8 `sqlite3` on the likely Nuremberg Linux host. This proposes no change to B1–B6, RF-D1–RF-D6, the GCS journal selection, or Home authorization. It is architecture only; there is no runtime code or deployment in this change.

## 1. Requirement recovered from the accepted decisions

[B4 §1](KNOWLEDGE_B4_FORGET_DELETE.md#1-summary-of-the-accepted-decision) requires a **durable suppression register as the authoritative non-use fact**, separate from asynchronous evidenced erasure. Its exact [C1 invariant](KNOWLEDGE_B4_FORGET_DELETE.md#121-the-restore-freshness-invariant-c1) is:

> RESTORED DATA MUST NOT BECOME USABLE UNLESS THE SYSTEM CAN PROVE THAT THE SUPPRESSION / DELETION CONTROL STATE USED FOR RECONCILIATION IS AT LEAST AS CURRENT AS THE PAYLOAD BEING RESTORED.

Unknown freshness fails closed. Existing encrypted backups are an expiry commitment, not immediate deletion; current personal-deployment retention is `keep 7 daily / 4 weekly / 3 monthly` ([B4 D1](KNOWLEDGE_B4_FORGET_DELETE.md#16-product-architect-disposition)). The accepted [restore-freshness decision §11](KNOWLEDGE_RESTORE_FRESHNESS.md#11-relationship-to-pre-runtime-durability-obligation-1) states that the independent journal protects Knowledge-owned anti-resurrection control state, but **ordinary acknowledged admissions/writes and durable erasure/cleanup evidence** still need a production SQLite durability decision. [Technology Gate §27.3–27.4](KNOWLEDGE_TECHNOLOGY_GATE_SPIKE_REPORT.md#273-sqlite-configuration--selected-vs-tested-vs-production) explicitly did not select its spike settings (`WAL`, `NORMAL`, `busy_timeout=5000`) for production and requires choosing **and testing** the affected P13 write/cleanup path and composition inputs before runtime approval.

This decision addresses the local durability mechanism while retaining the accepted journal-first ordering and every-start freshness proof. It does not claim that any local filesystem makes a day-old database backup contain yesterday's ordinary writes after total disk loss.

## 2. Failure domains and assumptions

| Failure | Durable local commit | Off-host SQLite backup | GCS control journal |
|---|---|---|---|
| Process crash | SQLite WAL recovery retains committed transactions. | Independent copy. | Independent control authority. |
| Linux kernel crash / power loss | Retains committed transactions **if** SQLite sync and storage flush contracts hold. | Independent copy. | Independent control authority. |
| Local volume or whole-host loss | Lost with host. | Restores a consistent historical DB; ordinary writes since its consistency point may be lost. | Replays Knowledge-owned control decisions and prevents stale admission; does not reconstruct all payload. |
| Stale or wrong DB restore | Local bytes may be internally valid but stale. | Supplies a candidate, never freshness authority. | Independently proves `H(p)` and controls admission. |
| Backup target loss | Local DB continues; alert and repair off-host backup. | Unavailable. | Separate failure domain. |

**Minimum production path:** persistent, locally attached Linux block storage formatted ext4 or XFS with working SQLite POSIX advisory locks, coherent shared memory, truthful `fsync`/write-cache flush, enough free space for DB + WAL + backup staging, and no unsafe mount options that disable required barriers. A container may use a persistent host bind mount/volume with the same properties; its writable image layer or ephemeral filesystem is not the database path. Keep DB, `-wal`, and `-shm` on that same local filesystem and under one service identity. No NFS, SMB, network mount, cross-host shared volume, `tmpfs`, or per-file sync mechanism pretending to be a coherent SQLite volume. Confirm the actual Nuremberg volume, mount options, runtime user, disk flush behavior and container volume mapping before use. SQLite explicitly says WAL shared memory does not work across hosts on a network filesystem ([WAL documentation](https://www.sqlite.org/wal.html)); Linux notes that syncing a file alone does not necessarily persist its directory entry ([fsync(2)](https://www.man7.org/linux/man-pages/man2/fsync.2.html)).

This depends on honest storage flushes and intact hardware. `synchronous=FULL` does not defeat a lying device cache, media failure, operator replacement, or application bugs. Treat `SQLITE_IOERR`, failed sync, unexpected mode/settings, disk full, or integrity failure as non-acknowledged/uncertain and remove affected Knowledge from READY until recovery establishes what committed. No directory rename is part of normal SQLite transaction acknowledgement; the backup publication procedure below explicitly syncs its file and containing directory. Do not base commit durability on an application-level atomic rename or on assumed atomic sector writes; use SQLite's VFS and WAL protocol ([SQLite atomic-commit assumptions](https://www.sqlite.org/atomiccommit.html), [WAL format](https://www.sqlite.org/walformat.html)).

**Durability** means a returned local commit survives the stated process/OS/power failures on a sound volume. **Recoverability** means a consistent off-host DB copy plus a restore gate; with daily snapshots, non-journaled acknowledged data created after the last snapshot has a bounded but nonzero loss window after host loss. **High availability** means continued service through host failure. B4 needs credible durability and recoverability now; synchronous block replication, a standby writer, and managed HA storage are **not required** for this personal/family phase. If a future product promise requires zero ordinary-data loss on whole-host failure, that is a new replication/RPO decision, not something this journal provides.

## 3. Candidates

| Candidate | Acknowledged commit / crash safety | Backup and restore | Cost and fit | B4 disposition |
|---|---|---|---|---|
| **A — WAL + FULL + one serialized SQLite write/checkpoint lane + Online Backup API + encrypted off-host restic** | SQLite syncs the WAL on each commit; committed state survives process/OS/power crash under §2 assumptions. SQLite safely recovers an interrupted checkpoint. | Consistent single-file backup artifact includes committed WAL content as of one SQLite snapshot; journal remains independent. | One sync per write; reads coexist with writer; bounded checkpoint work. The one-lane rule is material for pinned SQLite 3.41.2. | **SELECT** after required validation. |
| **B — WAL + NORMAL + same backup** | Process-crash safe and consistent, but recent acknowledged ordinary writes/erasure evidence can roll back on kernel crash or power loss; control can replay from GCS. | Same backup correctness and restore gate. | Faster write path, but violates §1's outstanding non-control durability obligation. | **REJECT** for production acknowledgement semantics. |
| **C — rollback `DELETE` + `EXTRA` + Online Backup API + restic** | SQLite documents rollback `EXTRA` as durable where rollback `FULL` may not be; no WAL checkpoint or WAL-reset race. | Consistent online copy still required. | Readers and writer block each other more, with extra sync/directory work; weak fit for retrieval plus cleanup contention. A viable fallback if A cannot be validated on the pinned library. | **DO NOT SELECT**. |
| **D — WAL + FULL + raw file copy/filesystem snapshot** | Live transaction durability as A. | A coordinated crash-consistent, atomic volume snapshot containing DB + WAL can be viable if demonstrated. A raw live `.db` copy alone or sequential `.db`/`-wal`/`-shm` copies are not a coherent backup. | Requires snapshot integration and restore proof for no current benefit. | **REJECT** as the minimum mechanism. |

SQLite's [synchronous matrix](https://www.sqlite.org/pragma.html#pragma_synchronous) says `NORMAL` in WAL mode is consistent but can lose durability on power loss; `FULL` syncs each WAL commit; `EXTRA` adds rollback-journal directory durability but is equivalent to `FULL` in WAL mode. [SQLite's backup guidance](https://www.sqlite.org/backup.html) treats Online Backup API and `VACUUM INTO` as live-consistent alternatives. `VACUUM INTO` is useful for compact copies and deleted-content purging, but has greater CPU work and an interrupted output may be incomplete; it is not the scheduled mechanism here ([VACUUM documentation](https://www.sqlite.org/lang_vacuum.html)). Restic is the encrypted **transport/retention** layer for a completed artifact, not SQLite's consistency mechanism. A raw live copy of DB/WAL/SHM is excluded ([SQLite corruption guidance](https://www.sqlite.org/howtocorrupt.html)).

**Pinned-version constraint:** SQLite's current [WAL documentation §11](https://www.sqlite.org/wal.html#walreset) identifies a rare WAL reset corruption race affecting 3.41.2 when separate connections in different threads/processes write or checkpoint at the same instant. The frozen SQLite selection is respected. Candidate A therefore requires **exactly one serialized connection/lane allowed to mutate or checkpoint this DB**; ordinary writes, control application, cleanup, automatic checkpoints and manual checkpoints all enter that lane. Other live connections are read-only, with short read transactions; the Online Backup API's source connection only reads this DB and its destination is a different file. No external SQLite CLI, maintenance process, second container or backup connection may write/checkpoint the live DB concurrently. This topology avoids the documented concurrent writer/checkpointer trigger; it is a requirement to validate on the actual runtime, not a claim to patch SQLite. If the topology cannot be enforced, A fails the gate and the Board must revisit the profile rather than silently use the risky concurrency pattern.

## 4. Selected runtime profile

Apply and read back settings on **every** SQLite connection where they are connection-local. Establish WAL mode on initial DB creation and verify it on every start. Refuse READY when required settings cannot be established, including on restored databases.

```sql
PRAGMA journal_mode=WAL;           -- must return wal; persistent database mode
PRAGMA synchronous=FULL;           -- every connection able to write/checkpoint
PRAGMA wal_autocheckpoint=1000;    -- writer lane; PASSIVE auto checkpoint at 1000 pages
PRAGMA busy_timeout=5000;          -- milliseconds, every connection; timeout is an error
PRAGMA foreign_keys=ON;            -- every connection; enforce relational constraints
```

Use one in-process serialized writer/checkpointer connection. Mutations use `BEGIN IMMEDIATE`, apply all local rows for one operation (including the register and `L(p)` for a control mutation, or cleanup evidence) in one SQLite transaction, then require successful `COMMIT` before acknowledging. The journal append is durably accepted **before** beginning that control transaction. Do not split payload/control or receipt/revision updates across local transactions. No `synchronous=NORMAL`/`OFF`, `journal_mode=OFF`/`MEMORY`, `locking_mode=EXCLUSIVE` cross-host workaround, or multi-DB `ATTACH` transaction is part of this profile. `busy_timeout=5000` is a bounded wait, not evidence of a committed transaction: timeout/error has an uncertain external outcome until checked using the operation identity.

**Checkpoint policy:** keep `wal_autocheckpoint=1000` on the writer lane. Automatic checkpoints are PASSIVE and may be partial when readers hold an old snapshot; commit durability comes from the WAL sync, not from completing a checkpoint. Observe WAL size and checkpoint progress. If it grows persistently because readers prevent recycling, end/shorten those reads and request `wal_checkpoint(RESTART)` **through the same serialized lane** during a quiet interval, checking its busy/result values. Use `TRUNCATE` only for planned space recovery through that lane; no `FULL`/`RESTART`/`TRUNCATE` checkpoint runs concurrently with a writer. Do not delete, truncate or separately copy a live `-wal` or `-shm`. SQLite syncs WAL before copying pages to DB and DB before WAL reset; a crash mid-checkpoint recovers from SQLite's valid WAL/DB state ([WAL documentation](https://www.sqlite.org/wal.html), [checkpoint API](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html)). A failed/blocked checkpoint is monitored and retried; it never turns an otherwise successful FULL commit into a safe excuse to acknowledge an error.

`-wal` is persistent database state while live and on unclean shutdown; `-shm` is a rebuildable WAL index and is not recovery truth ([WAL file format](https://www.sqlite.org/walformat.html)). Normal start opens the original path with any surviving WAL for SQLite recovery **before** integrity checks. Operators must never discard a hot WAL to make the DB open. The backup artifact is different: the Online Backup API has already folded a consistent SQLite snapshot into a standalone destination DB, so it contains no source WAL/SHM sidecars.

## 5. Acknowledgement order and crash semantics

For a Knowledge-owned control mutation, the sequence is fixed by [restore-freshness §5.4](KNOWLEDGE_RESTORE_FRESHNESS.md#54-control-commit-protocol):

```text
create exact journal entry → GCS append confirmed durable/immutable
→ BEGIN IMMEDIATE; local control/payload effects + L(p) together; COMMIT under FULL
→ acknowledge to caller
```

Only a confirmed GCS create/read of the exact entry counts as journal acceptance. A timeout/post-send loss is ambiguous, never a successful acknowledgement; reconcile the exact immutable identity and `event_id` before retry. Only successful SQLite `COMMIT` counts as local acceptance. For ordinary non-journaled writes, the local FULL commit must finish before ACK. Commit/ACK outcome uncertainty is resolved by an idempotency/operation identity, not by issuing a second logically new mutation.

| Failure instant | Required restart/result |
|---|---|
| Before journal append | No journal entry and no local control mutation. Caller has no success. Restart verifies normally; no new control state is inferred. |
| During/after GCS append but before local commit | The append may be absent or present. If present, `H>L` legitimately; partition stays RECONCILING and replays the control entry idempotently before READY. Caller was not told success. If append outcome cannot be proven, UNVERIFIED/INCOMPLETE. |
| During SQLite commit | SQLite exposes either committed whole transaction or no transaction after recovery. If no commit, `H>L` and replay. If committed, `L=H`; ACK may be absent, so retry resolves the existing `event_id`/receipt. DB or journal contradiction blocks. |
| After commit before ACK | `L=H` on a sound local volume; retry returns the recorded outcome for the same operation identity, without a second append. If restoring an older backup, replay brings control up to H, but ordinary payload created after that backup may be unavailable. |
| After ACK | Process/OS/power crash preserves local transaction under §2. Disk/host loss may remove local DB; off-host backup restores a consistent prior point, with journal replay for controls. An ordinary post-backup acknowledged write is a disclosed RPO loss, not claimed recovered. |
| During checkpoint | SQLite reopens from valid DB+WAL; no manual sidecar deletion. Checkpoint failure/partial progress is operational, not a new control head. Verify integrity and H/L before READY. |
| During backup | Incomplete staging artifact is never published to restic. Source continues under WAL; next backup retries. |
| During restore | Staging/restored files remain quarantined. Failed/incomplete restore cannot be installed or marked READY; reattempt from a verified snapshot. |

**`L(p)<H(p)` is expected after a journal-first crash and after a historical backup restore.** Replay all entries `(L,H]` in order into the KN control register, with exact generation/hash/epoch/identity checks, idempotent application and durable FULL local commits. Retain restrictive anti-resurrection metadata even when its original payload/target row was absent from the backup; a missing target must never make the prohibition disappear. Re-queue erasure and re-evaluate restored/imported payload before use. The journal cannot recreate an admission, source document, provenance or other ordinary data it never recorded. For any replayed control event whose safe state cannot be reconstructed from the journal payload and available local data (notably a permissive supersession or an inconsistent target identity), **do not fabricate it or skip it**: keep the partition BLOCKED pending a source/domain-truth repair or an approved operator recovery. Do not treat replay as authority to invent lost non-control payload. Replay completion requires `L=H` plus all §7 admission checks.

**`L(p)>H(p)` is never normal under journal-before-local ordering.** It indicates wrong/truncated journal, impossible identity, or corruption: BLOCKED, no local-head trust, no automatic journal creation or destructive re-baseline. A gap, invalid hash, wrong generation/epoch or impossible partition identity is likewise BLOCKED. An unavailable or incomplete journal proof gives `H=UNKNOWN`: UNVERIFIED, including after a fresh startup; a running READY lease behaves only as already accepted in [RF §6.1](KNOWLEDGE_RESTORE_FRESHNESS.md#61-freshness--writer-lease). Permanent journal loss remains subject to RF-D4 and is not repaired here.

## 6. Minimum backup architecture

1. Keep the existing **daily systemd restic cadence** and current personal-deployment `7 daily / 4 weekly / 3 monthly` retention category ([deployment baseline](../DEPLOYMENT.md#off-box-backup), B4 D1). The actual retained snapshot schedule governs the stated backup expiry tail; no fixed number of days is promised. Report missed/failed runs. This is a minimum, not an HA or zero-RPO claim.
2. Take a live SQLite snapshot using Python 3.11 `sqlite3.Connection.backup()` / SQLite Online Backup API from a dedicated source **read-only** connection into a new, private, same-host staging file. The source snapshot includes committed main DB and WAL content at one SQLite consistency point; no source checkpoint or writer pause is needed. Complete the backup, close destination, run full `PRAGMA integrity_check` (single `ok`) and `PRAGMA foreign_key_check` (zero rows), and read schema version and per-partition `L` **from the destination artifact**, not from a live source that may have advanced. Record those values, snapshot time, and artifact hash in a private manifest. Manifest data are diagnostic, never an authoritative `H` proof. [SQLite backup API](https://www.sqlite.org/backup.html); [Python 3.11 backup interface](https://docs.python.org/3.11/library/sqlite3.html#sqlite3.Connection.backup).
3. Sync the finished artifact and manifest inside a private staging directory, atomically rename the **directory** to a completed name on the same filesystem, then sync its parent directory. Restic must see **only completed, closed directories**. A crash before publication leaves a disposable incomplete directory, never a candidate snapshot. The artifact is one SQLite DB plus its manifest; source `-wal` and `-shm` are not included. Do not put a live DB path directly into restic's file scan. If an implementation uses a filesystem snapshot instead, it would need a separately reviewed atomic, same-volume DB+WAL crash-consistency proof; it is not selected.
4. Send the completed artifact/manifest with existing client-side encrypted restic to the EU Hetzner Storage Box. The backup operator owns the restic repository password and backup credential in the existing root/infra-only custody; the Knowledge runtime neither reads nor writes the restic repository. GCS journal credentials/key remain separate and are not copied into the DB artifact. Preserve the existing operator escrow of journal key with DR secrets, as specified by [RF §7](KNOWLEDGE_RESTORE_FRESHNESS.md#7-logical-ownership-vs-physical-persistence). Storage Box's rejection as **authoritative immutable journal** has no bearing on its ordinary encrypted backup role.
5. Check each run's Online Backup API completion, integrity result, manifest/hash and restic success. Periodically restore an artifact on an isolated host and execute the full §7 gate against the independent journal with synthetic or authorized data. Restic repository checks and actual recovery drills test transport and operability; a successful restic upload alone does not prove a recoverable SQLite snapshot. Backup or check failure alerts but does not automatically invalidate a healthy live FULL-committed DB; a corrupt live DB does.

If other Knowledge-owned payload files are introduced, a DB-only artifact is not a complete backup of those files. The implementation must either include a consistent, version-bound artifact set in the backup or prove that referenced external sources are independently recoverable; absent required evidence keeps the affected partition out of READY. This proposal does not turn GCS into a general payload backup.

## 7. Restore and admission runbook

1. Fence the old writer/host as defense in depth, provision a host/volume satisfying §2, and restore a **completed** restic DB artifact plus manifest into a quarantine path. Verify restic recovery, manifest/hash, expected SQLite/schema identity, full `integrity_check` and `foreign_key_check`. A corrupt or incomplete artifact is rejected; try another retained snapshot. Never copy the source WAL/SHM from an unrelated point. This installation is an operator-controlled replacement, not a live raw copy.
2. Install the separately escrowed GCS journal key and runtime credential. Start Knowledge in STARTING/VERIFYING, with no Knowledge retrieval, disclosure, import, admission or control ACK. Startup reads back `journal_mode`, `synchronous`, checkpoint/busy settings and validates local DB integrity. Opening SQLite successfully is **not** admission.
3. For each partition, read its local `L(p)` and independently prove complete `H(p)` from the GCS journal, using the accepted complete-list/exact-next-lookup, generation/epoch, partition identity and authenticated hash-chain rules. Do not use the restic manifest, a mutable pointer or local revision as proof of H. A new writer epoch obeys the accepted previous-lease quarantine before any control acknowledgement.
4. `L=H`: verify the local control register's materialized outcome against the authenticated journal entries (deterministic replay/check, not a counter comparison alone), plus payload/reference consistency, current tombstones/restrictions and required source evidence. Any mismatch stays quarantined for repair; do not trust a correct counter beside missing suppression rows. Then re-evaluate restored content against suppression and current B1–B6 checks. `L<H`: enter RECONCILING; replay §5's controls into the register, re-queue erasure, withhold use, then repeat these checks after durable `L=H`. `L>H`, impossible chain/identity or unreconstructable replay: BLOCKED. Journal unreachable/incomplete proof: UNVERIFIED. A tombstoned partition stays deleted and is not readmitted.
5. Issue READY **only** for a partition satisfying [RF §6](KNOWLEDGE_RESTORE_FRESHNESS.md#6-exact-freshness-invariant): `L=H`, valid complete chain and generation, no required gap, and a fresh valid writer/freshness lease. Fresh Home authorization and the B6 pre-use/pre-disclosure barriers remain mandatory. Other partitions may recover independently. No stored READY flag in the backup is trusted.

Live corruption or failed SQLite integrity check blocks the affected DB from serving Knowledge; preserve forensic copies with access controls, restore a known-good artifact through these same steps, and never manually patch `L` to match H. A DB-wide structural failure may block all partitions because a trustworthy per-partition read is impossible. Journal corruption/impossible chain blocks the affected partition; temporary GCS unavailability makes it UNVERIFIED. Physical erasure may be re-executed, but an `ERASED` claim requires currently durable evidence and independent verification, not a receipt that existed only in a lost local WAL/backup.

## 8. Operational verification and remaining gate

Before recommending **closure** of obligation #1, execute the Technology Gate's required P13 write/cleanup re-validation and affected §27.2.1 composition inputs on the pinned Python/SQLite runtime and the actual Nuremberg storage topology. Measure local `FULL` commit p50/p95/p99 and tail behavior, periodic automatic-checkpoint spikes, concurrent read/cleanup contention, WAL growth and checkpoint starvation, backup duration/impact, and full restore/replay time. Exercise process kill, kernel/power-loss-equivalent crash tests on the actual volume where feasible, disk-full and I/O-error handling, `L<H` after a journal-first interruption, `L>H`, journal unavailable/corrupt, backup interruption, and a real restore drill. Verify the **single SQLite writer/checkpointer lane** including systemd jobs, backup source and admin tooling; this is essential on the pinned 3.41.2 WAL library. Confirm the underlying volume and flush assumptions rather than extrapolating spike timing.

Expect higher write/cleanup latency than the `NORMAL` spike due to one WAL sync per commit and occasional commit-triggered checkpoints. WAL still permits short readers alongside the one writer; journal append remains an additional off-host step for control operations. No benchmark value is inferred from this choice. Separate pre-runtime obligations for direct warm/cold end-to-end latency and real R14/domain measurement remain OPEN; this decision does not discharge either.

**Proposed Board disposition:** ACCEPT Candidate A as the production SQLite durability profile and this backup/restore gate. **Pre-runtime obligation #1: REMAIN OPEN** until the specific §27.3 validation and Nuremberg storage/restore drills pass; then the Board can close it without choosing a new profile. No implementation or production deployment is authorized by accepting this architecture proposal.
