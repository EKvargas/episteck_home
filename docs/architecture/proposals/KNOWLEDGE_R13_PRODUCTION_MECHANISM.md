# Knowledge R13 production mechanism — architecture decision for Board review

**Date:** 2026-09-27
**Baseline:** `origin/main` `0db28ab21462c2ff74add1ecb07c215b8c64488a`
**Scope:** pre-runtime obligation #4 only. No Knowledge runtime, production service change, certificate issue, cloud resource, production data, or deployment is included.
**Recommendation:** **CLOSE #4 as a mechanism-selection obligation**, subject to Architecture Board acceptance. Production rollout remains a separate implementation approval. Obligations #2, #3 and #5 remain open.

## 1. Exact governing contract

The [B6 accepted retrieval contract](KNOWLEDGE_B6_TRUSTED_RETRIEVAL.md) distinguishes a complete Authorization Operation, a plan containing independently complete operations, and a Home network crossing (§8.3.2). Each operation is all-or-nothing; a plan may evaluate OP-K and several domain operations in **one** RT#1 without manufacturing a partial grant. Protected metadata planning must identify the complete requirements before RT#1. Home retains the trusted actor, machine caller, partition, requirements, and bounded request context (§8.4). The caller does not resupply actor or partition to Home. `decision_id` is correlation only.

The domain owner must verify that **this exact operation** was freshly approved by Home without another Home call in the ordinary execution path (B6 §18A.3a). Possession of an execution artifact alone is insufficient: verification must also use independently trusted server-side service identity or equivalent key confirmation. A token accepted merely because its signature and TTL check out would reproduce the rejected bearer alternative. The domain still enforces its own repository boundary. The original human delegation stays single use and is not replayed or extended.

The basis only permits the preapproved **read to execute**. Immediately before disclosure, Home RT#2 freshly reevaluates every contributing complete operation against current grants and policy, and the selected Knowledge versions pass suppression, lifecycle, classification, applicability and dependency checks (B6 §11). An earlier decision or unexpired basis cannot substitute for this barrier. If revocation ordering is unknown, withhold. Ordinary reads target **two Home network crossings**, independent of domain fanout; exceptional source expansion and writes retain their separately declared budgets (B6 §§18A.4, 18A.10).

The [Technology Gate report](KNOWLEDGE_TECHNOLOGY_GATE_SPIKE_REPORT.md) §14 showed a local, synthetic mTLS and Ed25519 composition, including an authenticated `svc-attacker` using a genuine `svc-nutrition` basis and signing key. Its in-process `R13-B` classification remains UNKNOWN because the identity parameter there was caller supplied; the later live TLS test was loopback only. The report's §21 and §27.4 explicitly left production identity, distribution and rotation open. Its `holder_of_key.py` `ExecutionBasis` is a plain dataclass without a Home signature, and its replay set is in-process; those primitives are **experimental evidence, not this production design**. [Phase-1 §11.4.1](KNOWLEDGE_TECHNOLOGY_GATE_PHASE1.md) requires the accepted service/key pair to come from trusted registration, never a request payload.

## 2. Current identity fabric and the missing link

The [repository inventory](KNOWLEDGE_R13_IDENTITY_INVENTORY.md) records source-by-source evidence and distinguishes documented live configuration from inference. Home MCP and Nutrition have **separate Frappe API User key/secret pairs**; their `Authorization: token key:secret` authenticates a machine caller **to Home**. Nutrition currently sends its own credential and the opaque, single-use human delegation to `check_access` before each sensitive repository read. The BFF is a confidential OAuth client; its browser cookie is opaque, and it HMAC-signs short-lived human delegation that Home verifies and single-use claims in Redis. Home resolves the human Frappe User/Person server-side. The human actor is **not** the service principal.

The Nuremberg services run under separate Linux users in rootless Podman. The local nginx gateway, UID/nft rules and a restricted Unix mint socket protect the delegation path; Tailscale routes Nuremberg↔Ashburn and existing Home calls still verify the Home TLS hostname. These are useful isolation and routing controls. **Inference:** neither Tailscale reachability, a Linux UID, a bearer Frappe key, nor a forwarded service-name header proves to a domain that the presenter possesses the service key Home bound to an operation. No production R13 CA or mTLS client-verification path is selected in the baseline. Existing mode-600 per-service secret files and infra-only backup custody are suitable custody patterns for the new keys, subject to the separation below. See [DEPLOYMENT](../DEPLOYMENT.md), [SECURITY_AND_CONSENT](../SECURITY_AND_CONSENT.md), and the inventory for precise code citations.

## 3. Options considered

| Option | Non-bearer / binding / replay | Distribution, rotation, revocation, blast radius | Topology, latency, operations | Decision |
| --- | --- | --- | --- | --- |
| **A. Direct mTLS service identity + Home-signed basis** | Verified client certificate proves private-key possession. Home signs exact request/actor/partition/subject/resource/domain/action/audience and binds registered service identity **and** client SPKI hash. Domain checks both, then atomically claims execution ID. A copied basis cannot pass without the bound key; attacker cert with copied identity text fails. | Separate internal service CA and Home signing key. Cert and signing-key rotation overlap by `kid`/SPKI; local signed revocation/trust snapshot must be current. Stolen caller private key affects that service's permitted operations until revoked, never other service identities. Home signing-key theft can forge approvals for any operation, so its custody is stricter. | Direct TLS verification inside the domain's trust boundary works with rootless Podman and current Nuremberg local calls, and extends to multiple hosts. Tailscale remains routing, not identity. One local TLS handshake can be reused; no Home verification call. Requires internal CA/runbook and domain TLS listener. | **SELECTED**. One service key is the transport proof; no second application signing key is necessary. |
| **B. Per-service Ed25519 request proof + Home-signed basis** | Domain verifies method, target, body hash, nonce and basis hash with a Home-registered key. Requires an *independent* authenticated service context; a request-provided service name/key alone fails §11.4.1. Replay ledger still required. | Per-service key distribution plus an independent machine-auth mechanism and Home signing trust. Two credentials and rotation paths per caller unless the same TLS key is reused. Compromise and revocation scopes comparable to A if implemented correctly. | Can traverse an nginx seam, but the present gateway proves a local UID/socket boundary, not a portable service identity. Adding authenticated identity forwarding or a second verifier increases the current operational surface. No extra Home call in principle. | Viable fallback, not selected. The old holder-of-key spike alone cannot prove its production identity binding. |
| **C. Existing Frappe machine credential + cryptographic PoP** | Existing API key identifies the service only at Home; a domain cannot validate it locally without receiving/verifying secret material or calling Home. Binding an additional proof key still needs trusted identity/key registration. Bearer key possession alone cannot count as non-bearer proof. | Copying Frappe secrets into domains expands compromise radius; rotation currently follows Frappe credentials, not offline domain trust bundles. | A Home lookup adds N crossings; distributing credential verifiers exposes Home secrets to domain owners. Rootless and Tailscale do not remove this. | Reject as the primary mechanism. Keep Frappe credentials for current Home API authentication. |
| **D. Unix peer/UID identity** | Kernel peer credentials could independently identify a co-located process, with Home-signed basis and durable replay. | Per-host UID policy and socket permissions are manageable, but UID identity does not cross hosts and container namespaces require explicit mapping. A local-only credential cannot be the production-wide service identity. | Local hardening only. |

Tailscale node identity, nginx header, or Home-brokered reference** | Node reachability is not per-service identity; a forwarded header is caller-controllable without a tightly authenticated proxy hop. A Home reference resolves safely only with another Home call. | Tailscale/gateway already exist; identity translation would need a new trusted proxy protocol and revocation model. | Home resolution returns to `2 + N`; replicated authorization is stale. | Not an R13 solution. |

All viable options must compare the **local server's fixed audience**, trusted actor/partition retained by Home, the exact request and operation, and a current signing/trust version. A valid basis for one audience cannot be presented to another. Option A has a single proof mechanism at the domain and the smallest verifier for the current topology; selection is based on that boundary and lifecycle, not on which option the old experiment chose.

## 4. Selected production identity and execution basis

The R13 caller is a dedicated trusted orchestration service identity, `spiffe://episteck.internal/service/olin-runtime` (name reserved by this design, **not provisioned**). The URI is a service-name profile, not a claim that SPIRE or a SPIFFE workload API is deployed. It is distinct from `home-agent`, the model, the browser, BFF's OAuth client, the Home MCP Frappe API User, and Nutrition's own Home API User. Future trusted orchestrator instances may share this logical identity only under a controlled certificate/key policy; issuance records instance and key version. Each domain has its own fixed audience URI, such as `spiffe://episteck.internal/service/svc-nutrition`. The domain's TLS listener requires a client cert chaining to the dedicated internal service CA, verifies clientAuth EKU, exactly one approved URI SAN, validity and local revocation state, and passes the verified peer identity and SPKI hash from the live connection directly to its verifier. A gateway may route bytes but must not terminate the client-authenticated connection or supply identity via headers. A later TLS terminator design requires a separately reviewed, authenticated local identity handoff before use.

Home RT#1 returns **one signed basis per allowed downstream operation**, never for a denied operation. The signer is Home-owned Ed25519; the domain has an out-of-band pinned verification-key set. Format is a versioned, deterministically encoded envelope with `home_kid`, `claims`, and `signature` over the exact encoded claims with an R13 domain-separation prefix. A canonical CBOR or strictly canonical JSON profile may be implemented; parsers must reject duplicate fields, unknown versions, noncanonical encodings, malformed signatures and unsupported algorithms. The spike uses canonical JSON for the local proof only. The private Home signing key is never held by the orchestrator or domains.

| Claim | Required meaning/check |
| --- | --- |
| `version`, `home_kid`, signature | Accepted format and active Home verification key; unknown/revoked key denies. Algorithm is fixed by version, not token input. |
| `execution_id` | Unpredictable unique ID, atomically single-use at this audience. Never the `decision_id`. |
| `request_id`, `plan_id`, `operation_id` | Home-retained request context and independently complete operation. Domain compares the signed IDs with the exact invocation; plan ID cannot be used to expand scope. |
| `actor_person_id`, `partition_id` | Trusted values from Home's consumed delegation and retained context, never model/caller claims. Domain uses them only as signed parameters for this operation, not as a new human login. |
| `subject_person_ids` / `resource_ids`, `domain`, `action`, `use_class` | Complete requirement set and exact domain read. Multi-subject operations stay indivisible. Domain matches its own resource routing and repository arguments; no dropped tuple or broader query. |
| `audience` | One fixed owning domain service URI. Domain compares its locally configured identity. |
| `caller_service`, `caller_spki_sha256` | Pair from Home's trusted service registration, **not** from an RT#1 payload. Domain compares URI SAN and SPKI of the verified mTLS peer on this connection. |
| `method`, `target`, `request_sha256` | Bind exact endpoint and canonical operation body including subject/resource/query parameters. Domain recomputes from the actual invocation before repository access. |
| `issued_at`, `expires_at` | Trusted Home time, at most 60 seconds from issue and no later than the Home-owned request window. Verifier permits at most 5 seconds of positive clock skew at issuance and never permits use at/after expiry. |
| `authorization_revision`, `window_id` / fence | Names the RT#1 state that approved execution and its bounded window. It is audit/fence data, **not** proof of fresh disclosure authority. If a domain-local invalidation is known, deny; RT#2 still performs current-state revalidation. |
| `decision_id` | Optional audit correlation only. Removing it changes no acceptance predicate. |

The signed basis travels only in trusted server-to-server memory/transport for this request. It is absent from browser responses/state, MCP or model context, `ContextBundle`, logs, traces, error payloads, and persistent Knowledge assertions. Metrics log only a redacted `execution_id` hash and outcome class. The domain must not echo the basis or any sensitive subject/resource identifier to an unauthenticated caller. TLS server authentication is required on the caller side as well as client authentication on the domain side.

## 5. Non-bearer proof and local enforcement

The domain acceptance predicate is:

```text
verified Home signature and active kid
AND authenticated TLS client chain/EKU/URI SAN/active key
AND (peer URI SAN, peer SPKI hash) == signed (caller_service, caller_spki_sha256)
AND signed audience == this domain's configured identity
AND signed exact operation == actual repository request
AND issue/expiry/window valid
AND atomic single-use execution_id claim succeeds
AND domain's own resource/partition guard succeeds
```

No field in the HTTP body or header may replace the TLS-derived peer identity, public key, actor or partition. A caller can copy the basis, payload and a false `service_identity=olin-runtime` string, but an authenticated `svc-attacker` TLS connection still has `svc-attacker` URI/SPKI and fails. A different trusted cert with the same URI but a different key also fails the SPKI comparison; untrusted cert or absent cert fails the handshake. The genuine key/cert with exact operation succeeds. A compromised genuine caller identity is a service compromise and enters the revocation path, not a property a non-bearer protocol can override.

The replay ledger belongs to the domain, with an atomic unique insert of `(audience, execution_id)` before repository access. For the current one-instance-per-domain topology, a protected durable local SQLite ledger can retain entries until expiry plus skew/restart safety. On collision, I/O error, corruption, or unavailable ledger, deny. A crash after claim may forfeit the operation; retry requires a new Home-approved operation, never reuse. Concurrent duplicates yield exactly one successful claim. If a domain becomes active on multiple hosts, the ledger must first become **shared and strongly consistent in-region** or execution must be single-writer routed with enforceable fencing; independent host-local ledgers are invalid. This does not involve Home.

## 6. Ordinary read sequence and counters

1. Trusted runtime receives a server-side delegated human context and resolves protected metadata without exposing content. It constructs complete OP-K and OP-N/OP-D requirement sets with exact domain request descriptors, then sends one Authorization Plan to Home **RT#1**.
2. Home consumes the original single-use delegation, resolves actor and partition, evaluates each operation all-or-nothing, retains the request-scoped context, and returns independent decisions plus signed bases **only** for approved domain operations. Unknown requirements deny their operation; no salvage of a compound question.
3. The runtime executes Knowledge locally and approved domain reads concurrently. Each domain verifies the live mTLS peer, Home signature, audience, exact operation/body, bounded lifetime, service/key pair, revocation and atomic replay state. It then applies its own repository guard and reads. **No domain-to-Home authorization call occurs.** The existing Nutrition path continues for all non-R13 calls until a separately approved production implementation uses this verifier.
4. Rank/select exact versions and contributing domain results. Home **RT#2** freshly reevaluates every contributing complete operation against current authoritative state using Home's retained actor/partition and revocation ordering fence. A denial/unknown suppresses that operation's contribution; an indivisible compound operation is withheld whole.
5. Only after the fresh barrier does the trusted runtime construct the `ContextBundle` and expose permitted content. A `decision_id` or basis never authorizes this step.

For ordinary P1/P2/P3 the future benchmark must assert `home_auth_round_trip_count == 2`, `authorization_operation_count >= domain_call_count + 1` for P2/P3, and no growth in Home crossings as domain calls grow. The additional `+1` is OP-K. Count crossings **at the actual Home client transport**, not by assuming two from an orchestration diagram; count logical operations independently from RT#2 reevaluations and count domain calls at their transport. Record signed-basis verification, replay, TLS handshake/reuse and domain repository latency separately. Run warm/cold end-to-end on realistic Nuremberg↔Ashburn topology under obligation #2, including 0/1/3+ domain fanout and failure paths. This spike does **not** execute or close #2, #3 or #5.

## 7. Failure and adversarial semantics

All listed failures deny the affected complete operation **before repository access**. If a contributing result later lacks fresh RT#2 proof, withhold disclosure. External error shape must not leak authorization/resource existence; obligation #3 still owns timing closure.

| Condition | Deterministic domain/runtime result |
| --- | --- |
| Missing, malformed, noncanonical, oversized basis; unsupported version/signature algorithm | Deny. No fallback to `decision_id`, existing delegation, or a Home lookup hidden inside the domain read. |
| Unknown/revoked Home `kid`, bad signature, stale verification bundle | Deny; operator distributes a trusted key bundle out of band. |
| Missing/untrusted client cert, wrong URI SAN/EKU, wrong key/SPKI, revoked service key, service identity mismatch | TLS rejection or domain denial. A body/header service claim is ignored. |
| Wrong audience, actor, partition, subject/resource, domain/action/use class, operation/request/plan ID, endpoint/body hash | Deny whole operation. Validate every signed field against configured service and actual request/repository arguments; do not truncate. |
| Expired basis, issue time too far in future, lifetime above 60 s, request window closed, clock unhealthy or skew beyond 5 s | Deny. Clock synchronization failure is an authorization uncertainty, not a grace period. |
| Replayed execution ID; duplicate concurrent execution | Atomic ledger admits at most one. All later contenders deny; no second repository read. |
| Domain restart | Durable ledger survives restart; if it cannot be opened/validated, deny. In-flight claimed operation may be lost. |
| Trusted-runtime restart | Discard in-memory bases. Resume through a new Home request/delegation; never replay an old basis. |
| Basis leaked to another service | Other service's cert identity/SPKI mismatches; deny. If leaked to browser/model, there is also a boundary incident, but possession cannot execute without the service key. |
| Verifier, TLS validation, revocation snapshot, replay ledger or local trust configuration unavailable | Deny. Never silently fall back to the existing domain-to-Home call inside an R13 ordinary read or skip domain enforcement. The application may explicitly take a separately measured legacy path with its truthful `2 + N` count. |
| Home authorization/key rotation during request; revocation accepted before disclosure | RT#2 decides current authority/fence. A revoked signing key or service cert immediately denies local execution once local trust state receives revocation; uncertain distribution suspends R13 reads. |

## 8. Key, trust and operational lifecycle

**Ownership/provisioning.** An infra operator owns an internal service CA trust root, separate from the Home signer. The root private key is kept offline and infra-only; issuance/revocation occurs through a reviewed operator procedure, not an HTTP request or model tool. The trusted runtime generates its own client private key under its dedicated rootless service UID. Each domain generates its server key under its own UID; the CA signs distinct serverAuth/clientAuth leaf profiles with an approved URI SAN for service clients. Private keys live in owner-readable mode-600 files under `/srv/episteck/services/<owner>/secrets/`, mounted read-only into only that owner container. Directory access follows the existing per-service ownership pattern. No cert/key is provisioned in this task.

Home owns an Ed25519 basis-signing key under its Ashburn service identity, separate from BFF's delegation HMAC and Frappe API secrets. Only Home signs. Domain owners receive the Home **public** key set and service CA **public** chain; Home receives the operator-approved mapping `service URI → accepted client SPKI hash(es) → status/validity`, never a private service key. Domains receive a signed, versioned trust bundle containing active Home `kid`s, CA roots, service/key revocations and `not_after` no more than 24 hours after issue; they pin its trust root and reject stale/rollback bundles. The operator signs this manifest with a dedicated distribution key (separate from the CA and Home signer), uses the existing infra-controlled SSH path to stage it on Ashburn/Nuremberg, atomically replaces a root-owned local file, and checks each service's loaded generation before enabling issuance on a new key. Rootless services mount the file read-only. The trusted bundle's public verification key is installed out of band at service setup; neither a domain request nor a Home response can introduce a new trust root. This is an **architecture runbook**, not a provisioned distribution service. Public material is not authority by itself.

**Rotation.** Every key/cert has a unique version/serial. Client/server leaf certificates have a planned 30-day validity and renewal begins at least 7 days before expiry; this is a selected operational target, not a claim about current automation. Stage new Home public `kid` and new service cert/SPKI in the trusted bundles before use; Home and domains accept old/new only during a documented overlap bounded by at least the maximum 60 s basis lifetime plus 5 s skew and rollout delay. Switch issuance to the new Home signing `kid`; retire the old key only after all its bases expire and verifier bundles converge. For service rotation, register the new SPKI at Home, reload the domain trust view, switch the caller cert, then revoke the old SPKI after the overlap. Fail closed if rollout/acknowledgment is uncertain. No automatic acceptance of an unknown key to avoid outage.

**Revocation/recovery.** An operator can revoke a Home signing `kid`, service cert serial/SPKI or CA intermediate with a monotonically increasing signed trust-bundle generation distributed to domains. Domain verification checks local current state; stale or unreachable distribution disables R13 execution. Home stops minting for a revoked service key immediately. On service key compromise, stop that caller, revoke the key at Home and domains, issue a new service key/cert under the same logical URI only after incident review, and force new plan evaluations. On Home signer compromise, stop minting, revoke `kid` everywhere, rotate signer, invalidate outstanding bases and re-evaluate all requests. CA compromise requires replacing the trust root and reissuing affected service certs; isolate R13 reads while trust is uncertain. Neither a basis TTL nor RT#2 compensates for a stolen signer/private service key during the exposure interval.

The distribution-signing key is infra-owned, versioned and stored apart from both the CA root and Home signer. Its pinned public key changes only through a separately authenticated operator install, with old/new bundle signatures overlapping until all services acknowledge the new generation. A compromised distribution key can falsify trust material across domains: stop R13, replace the pin out of band, inspect Home and domain loaded generations, and reissue affected service/Home keys if trust integrity cannot be established. Revocation is **not instantaneous before a domain receives the new bundle**. The runbook must disable minting and affected routing immediately, publish the new bundle, await loaded-generation acknowledgments, and treat any unacknowledged service as unavailable; already minted bases have at most their 60-second execution window. This residual propagation interval is an operational risk the Board should explicitly accept.

**Backup/restart.** Back up the offline CA key in a separately encrypted infra-only recovery store with dual-control access; never store that copy with service private keys or the Home signer. Home signing private-key backup, if retained for disaster recovery, is separately encrypted and access controlled; recovery must force rotation and trust-bundle publication before use. Service private keys are **not** restored from ordinary service/data backups: reissue on rebuild. Back up public trust manifests and operator issuance/revocation records; a restored old bundle must be rejected by generation/freshness checks. Replay ledger is security state and must survive routine process restart, but must **not** be restored to a snapshot that forgets unexpired claims. A disaster restore with uncertain replay state denies R13 until all potentially outstanding bases have expired plus skew, or a strong shared ledger is recovered. Do not back up CA and Home signing keys together, and do not put private keys in Knowledge data, restic content sets used for family data, Git, logs or agent context.

Operational observability records plan/operation IDs as redacted correlations, outcome classes, trust-bundle generation, `kid`, service URI and hashed SPKI, replay collisions, TLS identity failures, and the three crossing counters. Logs never record basis bytes, private keys, human delegation or resource content. Alert on stale bundles, skew, certificate expiry, unknown `kid`, signature failures and ledger unavailability. Rootless container access to the required read-only key and durable ledger mounts must be validated before runtime approval; this decision does not alter the current Quadlets or Home/Nutrition configuration.

## 9. Decisive disposable evidence and limits

The new [local composition test](../../../spike/knowledge-technology-gate/scenarios/test_r13_production_shape.py) creates a throwaway CA with client URI SAN certs, a distinct Ed25519 Home signer, a Home trusted service/SPKI registration, a real loopback mTLS exchange, a domain verifier, and a local SQLite unique replay ledger. It reuses the old spike's ephemeral CA base and `HomeStub` plan evaluator. The client identity is derived from the **verified live TLS peer**, never from `wire["service_identity"]`; Home public verification material is configured out of band. No production service, CA, credential or data is contacted.

`python -m pytest scenarios/test_r13_production_shape.py -q -s` from `spike/knowledge-technology-gate` produced **12 passed**. Positive exact operation: authenticated runtime cert and registered genuine SPKI, signed Home basis, one repository read. Negative arms: no client cert/basis alone; authenticated wrong service with copied `service_identity` claim; same service URI with wrong key; wrong audience; replay (also after a domain restart); mutated operation; expired basis; forged Home claims; locally revoked service key. Wrong-service and wrong-key are separate checks. The old [transport case 2b test](../../../spike/knowledge-technology-gate/scenarios/test_r13_transport_case2b_closure.py) additionally tests the stronger attacker with a genuine Nutrition holder-of-key signature and a wrong authenticated TLS service.

The positive counter values are emitted by the tests and asserted from `HomeStub.evaluate_plan` and actual TLS domain calls, not assigned as a pass condition:

| Flow | `home_auth_round_trip_count` | `authorization_operation_count` | `domain_call_count` | Repository reads |
| --- | ---: | ---: | ---: | ---: |
| One approved domain operation, RT#1 + fresh RT#2 | 2 | 1 | 1 | 1 |
| Three approved domain operations in **one** RT#1 plan, fresh RT#2 | 2 | 3 | 3 | 3 |

The synthetic count proves the **mechanism** introduces zero domain-to-Home calls. It does not measure cross-region latency, prove the current production paths are cut over, or close #2/#3/#5. The spike uses a fixture in-memory revoked-key set and local one-process replay ledger; the production trust distribution and persistence rules above are normative design requirements requiring implementation verification. The old in-process `R13-B` verdict remains UNKNOWN for that old experiment; this selection rests on the new live mTLS composition and the separately documented operational design.

## 10. Board disposition

**Recommend #4 CLOSED** because a specific service identity mechanism (direct mTLS URI SAN + SPKI binding), Home-signed execution basis, key/trust lifecycle, non-bearer adversarial proof and flat Home-crossing count have been selected/demonstrated at the local mechanism scope. Board acceptance closes the *architecture selection* only. No production runtime or configuration is authorized by this recommendation.

The remaining implementation checks are concrete acceptance criteria for a future runtime/change review, not an unresolved R13 mechanism choice: deploy the dedicated CA and service cert lifecycle; configure direct domain mTLS and Home-signed plan responses; publish pinned, fresh trust bundles; ensure durable atomic replay state; validate rootless mounts and fail-closed behavior; instrument real transport crossings; then run obligation #2's warm/cold benchmark. Any failure to provide the independent authenticated peer identity or current trust state blocks runtime approval and reopens #4 rather than silently returning to a bearer basis.
