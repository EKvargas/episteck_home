# Knowledge Technology Gate — Empirical Spike

Authorized by TG-PA-7. See:
`docs/architecture/proposals/KNOWLEDGE_TECHNOLOGY_GATE_PHASE1.md` §16, §18.1.

## What this is

An isolated, synthetic, disposable experiment gathering the empirical evidence the
Knowledge Technology Gate needs to eventually select a persistence/retrieval technology.
It tests whether accepted B1–B6 security invariants (trusted partition, authorization-
constrained retrieval, suppression-before-candidacy, exact-version lifecycle,
materialization-binding currency, restore-freshness, non-bearer downstream execution)
hold under two real backends (SQLite, PostgreSQL), and measures latency shape.

## What this is NOT

- Not the final Knowledge technology selection.
- Not a production Knowledge runtime, schema, or service.
- Not a migration of any kind (including Nutrition preferences).
- Not a deployment.
- Not real family onboarding.
- Not a production R13 security mechanism (the Ed25519 holder-of-key experiment here is
  an experimental realization only; no production key-registration/PKI is selected).

## Isolation

- Runs off production. No connection to `home.episteck.com`, production svc-nutrition,
  the production gateway, or any production credential.
- Home and domain peers are **stubbed** in-process (`home_stub/`, `domain_stub/`), with
  latency calibrated from accepted repository measurements (E7 in Phase-1 §2.3), not real
  network calls.
- All data is synthetic, seeded, and generated by `corpus/generator.py`. No real Person,
  Circle, grant, preference, or health content.
- PostgreSQL scenarios run only against an already-available disposable Postgres detected
  by `backends/postgres_env.py` — this spike does not install, provision, or configure any
  database or container runtime. If none is available, PostgreSQL scenarios are marked
  `NOT EXECUTED — ENVIRONMENT BLOCKED`, not silently skipped or faked.

## Running

```bash
# from spike/knowledge-technology-gate/
python -m pip install -e .[dev]
pytest                          # correctness scenarios, closed-set PASS/FAIL/UNKNOWN
python bench/run_bench.py       # latency + counter benchmark matrix -> bench/report_data/
python teardown.py              # remove all spike-created state (sqlite files, temp pg db)
```

## Evidence classification

Every scenario/result is exactly one of:
`PASS` / `FAIL` / `UNKNOWN — INSUFFICIENT EVIDENCE` / `NOT EXECUTED — ENVIRONMENT BLOCKED`
/ `N/A`. `UNKNOWN` is never silently promoted to `PASS`.
