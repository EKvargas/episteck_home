# KAP-2 two-host PERSON acceptance package

**Status:** executable disposable package for architectural review; **not authorized for remote execution**. It tests the fixed transactional-witness plus default-closed incarnation candidate from consolidated PR #71. It does not add Home RT#1/RT#2, a Knowledge runtime, a production migration or a service unit. The [decision sheet](DECISION_SHEET.md) lists the approvals needed before the first remote command.

## Fixed scope and measurement

The Home side runs `home_runner.py` on **`ubuntu-4gb-ash-1` (Ashburn)**. The witness side runs `witness_runner.py` on **`ubuntu-4gb-nbg1-1` (Nuremberg)**. Each uses a new marked `/tmp/kap2-pr71-twohost-01` root and a private socket-only MariaDB instance. Only the witness exposes TCP: **the Nuremberg Tailscale IPv4 address, port `19442`, mTLS required**. The address is read on that host at execution time; no public interface or guessed address is allowed. Home makes outbound mTLS calls over the existing private mesh. The server certificate pins the literal Tailscale IP; `kap2-home-serving` and `kap2-home-recovery` are different, short-lived client certificates. The serving certificate cannot invoke recovery/control routes; the recovery certificate cannot authorize or mutate. The CA private key stays with the operator, never on either host.

The test listener process is the sole witness gateway. It begins volatile `CLOSED` even if MariaDB contains old permissive rows. `gw_reader`, `gw_writer2` and `gw_recovery` have different per-run random passwords and private procedure rights. `gw_writer1` is retained only to prove obsolete-epoch rejection. Home uses separate per-run `ha_reader`, `ha_mutator` and `ha_recovery` accounts; the serving mutator has no direct DML on authority sources. Its own private MariaDB has `--skip-networking`. Synthetic `site_runtime` exercises named generic-write guards. Only the temporary test-process OS user can enter the mode-0700 roots and local sockets. The runner temporarily holds both Home transport certificates to automate synthetic recovery; this is not a production credential-custody design.

The optional mandatory-for-remote `--bench` path points to a **separate disposable Frappe 15.99.0 bench** on Ashburn. The existing marked-site `run_frappe.py` exercises ordinary Home API, Person and session behavior and generic Frappe save/delete/`db.set_value`/SQL paths, then removes its site and two private databases. It is a compatibility control using local witness fixtures; it does not claim a remote RT endpoint or prove that all production Home mutation sources have been cut over.

### Predeclared acceptance matrix

Every required step is `PASS` only if its stated assertions execute. The runner exits nonzero on failure; later steps are then unexecuted, not implicitly passed. Home and witness JSONL evidence is flushed and fsynced after each step/request/sample so lost SSH stdout cannot erase it.

The client reserves every attempted HTTP request before sending, including denied role calls and the failed anonymous TLS attempt. There are **no automatic retries**. Both client and server enforce a hard **400-request** cutoff; the scripted latency screen accounts for 120 authorization requests and the remainder covers the fixed scenarios. The authoritative request totals are the fsynced Home `matrix_summary` and witness request events; TLS failures appear only in the Home ledger. Exceeding the cap, missing evidence or an unexecuted required step rejects the run. This is a bounded test budget, not a billing quota.

### Latency allocation proposed for review

The governing Authorization Plan contract §13 sets the **complete future pre-LLM path** at ordinary p95 ≤500 ms and initial p99 ≤800 ms, with p50 ≤300 ms as an aspiration. It does **not** allocate a KAP-2-only allowance. Before a remote run, propose a screening allocation of **one KAP-2 policy/witness call p95 ≤100 ms and p99 ≤200 ms; the measured synthetic pair p95 ≤200 ms and p99 ≤400 ms**. That reserves nominal room for planning, transport, domains, Knowledge and bundling, but percentiles cannot be added as a proof of whole-path latency. The allocation is **unratified** and the runner records distributions without changing a threshold after the fact. Thirty pairs make p99 effectively a maximum and do not pass KAP-10. Complete RT#1/RT#2 and Knowledge latency remain later gates.

## Prepared execution sequence — **do not run remotely without authorization**

1. On a trusted operator machine, record the exact approved PR head, derive the current Nuremberg Tailscale IPv4 from that host, and generate one-run Ed25519 CA/server/serving/recovery certificates with `python certs.py --out <new-operator-dir> --server-ip <NBG_TAILSCALE_IP>`. Keep `ca.key` on the operator machine. Verify the certificate IP SAN and file mode 0600. Copy only `ca.crt`, `server.crt`, `server.key` to Nuremberg; only `ca.crt`, `serving.crt`, `serving.key`, `recovery.crt`, `recovery.key` to Ashburn, into the exact certificate directories above. Keys and synthetic DB passwords are never committed or placed in evidence.
2. After separate authorization, create the transient OS users, acquire MariaDB binaries on Nuremberg, create the isolated Python environments and Ashburn Frappe 15.99.0 bench, clone the exact PR SHA into the temporary checkouts, and permit only Ashburn→Nuremberg Tailscale TCP `19442`. Verify the checkout SHA, free port, tools, absent roots, and no production path in arguments. The Nuremberg listener starts first and records `CLOSED` before Home begins.
3. As the transient user on Nuremberg, from the exact temporary checkout, run `python spike/knowledge-kap2-two-host/witness_runner.py --root /tmp/kap2-pr71-twohost-01 --evidence /tmp/kap2-pr71-twohost-evidence/witness.jsonl --bind <NBG_TAILSCALE_IP> --port 19442 --ca /tmp/kap2-pr71-witness-certs-01/ca.crt --cert /tmp/kap2-pr71-witness-certs-01/server.crt --key /tmp/kap2-pr71-witness-certs-01/server.key --expected-sha <APPROVED_PR_HEAD>` in a supervised foreground session. Do not use `--loopback-only` on the remote run.
4. As the transient user on Ashburn, from its exact temporary checkout, run `PYTHONPATH=/tmp/kap2-pr71-src-01/apps/episteck_home python spike/knowledge-kap2-two-host/home_runner.py --root /tmp/kap2-pr71-twohost-01 --evidence /tmp/kap2-pr71-twohost-evidence/home.jsonl --witness-host <NBG_TAILSCALE_IP> --port 19442 --ca /tmp/kap2-pr71-home-certs-01/ca.crt --serving-cert /tmp/kap2-pr71-home-certs-01/serving.crt --serving-key /tmp/kap2-pr71-home-certs-01/serving.key --recovery-cert /tmp/kap2-pr71-home-certs-01/recovery.crt --recovery-key /tmp/kap2-pr71-home-certs-01/recovery.key --bench /tmp/kap2-pr71-frappe-bench-01 --expected-sha <APPROVED_PR_HEAD>`. The runner's JSONL is primary evidence; stdout is optional.
5. Archive sanitized JSONL/result plus exact SHA and tool versions, then send SIGTERM to the witness runner. Each runner records `*_cleanup` and removes only its marked root. Remove the reviewed temporary certificate/checkout/bench/user/ACL inventory after checking resolved paths. Run `verify_cleanup.py` separately on both hosts with the exact root, certificate dir, evidence, host and port; pass `--bench`, `--source` and `--frappe-result` on Ashburn. A failed cleanup check remains an open task; do not claim closure from a process exit alone.

The test controls intentionally kill only disposable connections, restart the disposable gateway, and physically copy/restore only marked private MariaDB datadirs. An unexpected error fails the matrix and leaves evidence; no fallback admission or automatic retry is permitted. `--local --reset-local` exists only for iterative loopback development and is forbidden for the two-host acceptance run.

**Verify package files:** `python -m py_compile spike/knowledge-kap2-two-host/*.py` and `rg -n 'A0|A11|KAP-2 policy/witness' spike/knowledge-kap2-two-host/README.md`.

The fresh disposable loopback run and its limits are recorded in [LOCAL_VALIDATION.md](LOCAL_VALIDATION.md). It does not substitute for the authorized two-host gate.
