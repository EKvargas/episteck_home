# KAP-2 bounded witness: disposable Ashburn run, 2026-10-09

**Scope:** One isolated project `episteck-kap2-bnd-261009` (number `771685799600`), two `us-east4` regional buckets, one key ring, three separate SOFTWARE `EC_SIGN_ED25519` CryptoKeys/versions, five scoped service identities and an existing operator. Synthetic authority only. This is an integration experiment, not a Home endpoint or production fence. Base design: PR #62 at `b941b78613135363ed2c2ad2a99d317556cb8703`; PR #61 is the earlier full-scan/IAM evidence. The run used the actual Ashburn Home host `ubuntu-4gb-ash-1` and a private disposable MariaDB 10.11.14 socket/datadir under `/tmp/kap2-bounded-261009`. No production database, app code, grant, migration or credential was changed.

## Outcome and recommendation

**Reject Candidate A in its current request-time GCS form.** The safety schedules below were encouraging, but witness-only latency already exceeds the amendment's provisional 100 ms paired p95 / 200 ms paired p99 allocation at suffix 0 and rises above the governing whole-path 500 ms p95 target at suffix 8 before Home/domain work. A real `429` occurred while replacing the same head rapidly; Google documents a one-write-per-second rate limit for repeated writes to one object. Recovery retained the immutable slot and resumed without a competing history, but pacing the two head replacements per mutation introduces material write delay. These results do not pass KAP-10 and do not establish a production retention or trust design. Compare the independently operated transactional witness rather than activating this mechanism.

The real first process completed suffix 0 and 1 screens and then received `429` on a PENDING head replacement after creating slot 7. It failed closed. A fresh process re-read the current head and DB, verified that exact retained slot, advanced PENDING and COMMIT under the same partition lane, restored cumulative counters, and completed the remaining experiment. Both the adverse first result and recovery are preserved in [`events.jsonl`](events.jsonl). This is a measured recovery of one known orphan, not a general recovery implementation.

## Request accounting and adverse responses

[`summary.json`](summary.json) is produced by [`summarize_live_evidence.py`](../../summarize_live_evidence.py) from all five fsynced JSONL files. Across preflight, smoke, main, fault-read and stale-CAS runners, **3,974 object requests** were reserved before sending, counting failed attempts and the `429` retry path: below the hard **5,000** cutoff. The main run used **3,629 object GET, 144 immutable CREATE, 145 head replacement, 40 LIST and one other object request**. The other runs add 15 object requests. Thus every reviewed category cap (4,200/160/160/200) held even if the runs are combined. Main KMS sign attempts were old/new/checkpoint **129/5/9**, below 160 each; the smoke added one checkpoint sign. The main run also recorded 376 bucket metadata GETs; all five runners together recorded **395** bucket metadata GETs and 21 KMS public-key metadata GETs. Counting bucket reads with object GETs gives 4,035 GETs, still below 4,200. Bucket metadata was necessary to check the pinned project number, creation time, region and name before accepting an exact slot 404; it was absent from PR #62's original object-only ledger and adds to latency/cost.

Main responses included object GET 3,197 × 200, 431 × 404, one real `ReadTimeout`; CREATE 142 × 200 and two × 403; head CAS 143 × 200, one × 403 and one × 429; LIST 40 × 200; one journal DELETE × 403. The missing-bucket metadata request returned 404. Preflight first received a verifier bucket-metadata 403; a narrowly scoped `storage.buckets.get` grant corrected it before the smoke and measured run. The two deliberately stale head writes after takeover returned 412. The full runner, not operator setup/teardown CLI, enforced these counters. Cleanup used 145 object deletes plus inventory LIST operations; CLI internal retries were not instrumented and are not claimed as exact experimental counts.

## Ashburn latency screen

Milliseconds; each temperature/suffix group has 30 RT#1/RT#2 **pairs** and 60 individual candidate-reader calls. Each call reads the live head, signed checkpoint, two objects per suffix event, exact successor, pinned bucket metadata and the local MariaDB row. Cold starts a new HTTP client/pool/TCP/TLS connection before each pair; the two reads within a pair may reuse it. Warm reuses one client. Neither caches the head or successor absence. Values include local MariaDB and cryptographic verification but **exclude actual RT#1/RT#2 services, Home transport, domain execution and bundling**. Thirty samples make p99 effectively a maximum, not a stable percentile estimate.

Two full 64-event/9-checkpoint recovery audits each verified 137 signed journal objects, with 40 LIST requests total; wall times were **8,411 ms** and **5,168 ms**. They were separate from request-time authorization. The run consumed less than the 4,520 planned object-request budget because it needed fewer retry/adversarial requests than reserved. The rates underlying the design cost estimate are [GCS regional Standard operation pricing](https://cloud.google.com/storage/pricing) and [Cloud KMS pricing](https://cloud.google.com/kms/pricing); final billed charges have not settled. The project-filtered **€4.47** budget alert (approximately $5 using the [ECB 2026-10-08 reference rate](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.ff.html)) was a notification, not a cap. The CLI initially parsed `4.47` as 47 nanos; the amount was corrected and verified as 4 units + 470,000,000 nanos before storage/key provisioning.

## Safety schedules: measured versus injected

| Schedule | Result and evidence limit |
| --- | --- |
| Fresh permissive authority, exact successor absent | **ALLOW** on smoke prefix with real GCS checkpoint signature, pinned bucket metadata and MariaDB row. |
| Two publisher database connections | Second `SELECT ... FOR UPDATE` timed out after at least 500 ms while the first held the private MariaDB row; it proceeded after release. This tests DB lane contention, not production connection drainage. |
| Permissive COMMIT gap and restrictive revocation gap | With an otherwise permissive takeover event, DB commit + PENDING head denied; matching COMMIT then allowed. Revocation gap denied; after matching COMMIT the revoked row still denied. |
| Publisher connection loss after immutable PREPARE slot | Closing the private MariaDB connection rolled back its uncommitted transaction; the retained successor slot blocked the old head. This is controlled connection loss, not process/host failure. |
| Combined Home/head rollback after revocation | Restored synthetic permissive MariaDB row and prior valid head by current-generation CAS; retained revocation slot was present, and authorization denied. Current revoked state was then restored and still denied. No retention policy or lock was set, so production nondeletability remains unproved. |
| Takeover while old signer still works | Old KMS signing returned 200 after epoch transition. Candidate publisher rejected the old identity by epoch check; old writer direct journal/head attempts returned 403. Separately delayed stale-generation head writes for pre-takeover sequences 64 and 65 returned 412. This does not prove a compromised publisher's valid-current-generation behavior or complete in-flight drain. |
| Credential isolation | Head-overwrite identity journal DELETE and replacement both returned 403; old writer journal append and head replacement both returned 403. The test excludes project owner credentials and trusted-code compromise. |
| Missing bucket, wrong incarnation, permission error, timeout, malformed response | A real nonexistent journal bucket returned 404 and denied; a real unprivileged verifier-token swap returned 403 and denied; one live head GET with an extremely short deadline produced `ReadTimeout` and denied. Wrong-incarnation mismatch and malformed 200/head payload were **locally injected** against a permissive smoke snapshot and denied. No naturally malformed GCS response or uncontrolled outage was observed. |
| Lost publication acknowledgement | The first 429 was a known rejected response, not a lost acknowledgement. The runner has exact-byte 412 readback logic, but no controlled post-acceptance response-drop test was executed in this run; PR #61 has earlier live create-response-loss evidence for a different protocol. |

The prototype uses a synthetic in-process trusted publisher and operator-pinned KMS public keys. Checkpoints are signed but do not form a production-validated checkpoint hash chain. The run does not establish database-enforced publisher privilege coverage, authenticated historical signer registration after restore, durable journal retention, production reader deployment, or a production recovery procedure. A signature alone is not freshness. No synchronous request-time full scan was used.

## Cleanup and residual state

Before deletion, exact inventory showed **2 head** and **143 journal** objects, all under the two checked `SYNTHETIC-KAP2-*` prefixes. Their archive hashes matched the Ashburn copies. All 145 objects and both buckets were deleted; post-delete object lists were empty. Three KMS versions were changed from ENABLED to **DISABLED**, with no irreversible destruction. All three key-scoped signer bindings, five service identities, three custom roles and the budget were removed; lists showed no buckets, service identities or matching budget. The private MariaDB process was shut down and its exact resolved `/tmp/kap2-bounded-261009` directory removed after archive verification. The isolated project was deletion-requested; `gcloud projects describe` returned **`DELETE_REQUESTED`**, and billing returned **`billingEnabled: false`**. Key rings, disabled keys, cloud audit metadata and final billing may remain as asynchronous project-deletion residue. No production resource was touched.
