# KAP-2 journal signing trust candidate

**Design for integration testing, 2026-10-08.** No production key, trust registration, bucket or service identity exists. This does not approve KAP-2 activation.

## Trust anchor and registration

Select a Home-owned offline Ed25519 registration root. Its public key fingerprint and PEM are pinned by the verifier's independently controlled deployment configuration and recovery kit, outside MariaDB and outside the GCS journal. A public key carried in a journal object is never itself an anchor. Keep the root private key offline under two-person operator custody with a documented restore drill; the journal writer has no root signing permission. A lost root private key blocks new registrations but does not invalidate historical verification while the pinned public root survives. Loss or disagreement of the pinned root blocks all authorization reads until independently approved recovery establishes a new anchor.

For each writer epoch, the custodians sign a canonical registration payload under the domain `KAP2_REGISTER_V1\0`. It binds protocol version, partition, monotonically increasing signer epoch, exact Cloud KMS key-version resource name, Ed25519 public-key PEM, and prior registration SHA-256 (`GENESIS` for epoch 1). Publish the envelope with `ifGenerationMatch=0` at `home-auth/v1/partitions/<id>/trust/<20-digit-epoch>.json`; read back exact bytes. A verifier first checks the independently pinned root DER SPKI SHA-256, root signature and chain, then compares the registered PEM to KMS `getPublicKey` while that version is enabled. Preserve each verified registration object and public key in an independent operator recovery archive with checksum and access audit. [Cloud KMS supports `EC_SIGN_ED25519`](https://docs.cloud.google.com/kms/docs/algorithms); [public-key retrieval requires an enabled version](https://docs.cloud.google.com/kms/docs/key-states), so historical verification must not depend on a later KMS fetch.

## Journal signatures and rotation

The Home writer uses a dedicated Cloud KMS `ASYMMETRIC_SIGN` Ed25519 key version. Only its scoped service identity may call `cryptoKeyVersions.asymmetricSign`; it has no key administration or destroy permission. Every slot and outcome envelope contains a canonical payload, the SHA-256 of its root-verified registration, and a KMS signature over `KAP2_JOURNAL_V1\0 || canonical(payload)`. The verifier selects the public key *only* through the root-verified registration map, validates signer epoch and partition/sequence/hash chain, and denies on missing, conflicting, unknown, or invalid signatures. [KMS asymmetricSign](https://docs.cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys.cryptoKeyVersions/asymmetricSign) accepts raw data for this algorithm and returns the exact version name; the runner checks that name and locally verifies the signature before publication.

Rotation requires a root-signed epoch `n+1` registration pointing to epoch `n`; a new KMS version and separately scoped writer identity; a drained old write lane; and a unique conditional EPOCH slot signed by the new key. Revoke the prior writer's signing and object-create permissions before admitting the new epoch. A late old writer can at most occupy an immutable next slot and block progress; it cannot create a second authoritative slot. Old public keys remain available for verification, while old private key versions can be disabled after cutover. Destruction timing must exceed the journal evidence and recovery policy; the [KMS destroy schedule](https://docs.cloud.google.com/kms/docs/destroy-restore) is not a substitute for archived public keys or independent witness retention. An emergency root rotation requires an out-of-band independently authenticated new pin, dual operator approval, and a blocked serving lane until the entire registration chain is revalidated.

## Restore and failure behavior

After any MariaDB restore, load the independent pinned root, discover and verify the full GCS registration and signed slot/outcome chains, and compare the latest committed witness sequence with the local partition fence before allowing disclosure. Database-restored keys, READY flags and grant rows provide no trust. Missing root pin, unavailable GCS, missing historic registration/public key, unknown signer epoch, signature mismatch, incomplete outcome, or local revision mismatch all deny and require operator recovery. Recover MariaDB only to a state reconciled with the witness; never backdate the witness to match the DB. Preserve the root pin and registration archive in recovery material with a separate access path from DB backups.

## Evidence boundary

Local synthetic tests verify that a self-signed attacker registration cannot replace the pinned root, that signed payload tampering fails, and that two registered epochs verify from the root and registration material without consulting database state. The GCS runner is prepared to conditionally publish two root-signed registrations, compare both against KMS public keys, sign/verify journal objects, and scan the signed history. It retains the 160 create-attempt and 5,000 object-request caps and uses synthetic partitions. **No live KMS/GCS signing, IAM, timeout, retention, rotation isolation, key recovery, or history latency has been run.** The current runner signs both epochs with one probe service identity; old-identity exclusion requires a separate authorized integration step and cannot be inferred from cryptographic rotation alone.
