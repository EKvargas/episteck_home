# KAP-2 journal signing trust candidate

**Design for integration testing, 2026-10-08.** No production key, trust registration, bucket or service identity exists. This does not approve KAP-2 activation.

## Trust anchor and registration

Select a Home-owned offline Ed25519 registration root. Its public key fingerprint and PEM are pinned by the verifier's independently controlled deployment configuration and recovery kit, outside MariaDB and outside the GCS journal. A public key carried in a journal object is never itself an anchor. Keep the root private key offline under two-person operator custody with a documented restore drill; the journal writer has no root signing permission. A lost root private key blocks new registrations but does not invalidate historical verification while the pinned public root survives. Loss or disagreement of the pinned root blocks all authorization reads until independently approved recovery establishes a new anchor.

For each writer epoch, the custodians sign a canonical registration payload under the domain `KAP2_REGISTER_V1\0`. It binds protocol version, partition, monotonically increasing signer epoch, exact Cloud KMS key-version resource name, Ed25519 public-key PEM, and prior registration SHA-256 (`GENESIS` for epoch 1). Publish the envelope with `ifGenerationMatch=0` at `home-auth/v1/partitions/<id>/trust/<20-digit-epoch>.json`; read back exact bytes. A verifier first checks the independently pinned root DER SPKI SHA-256, root signature and chain, then compares the registered PEM to KMS `getPublicKey` while that version is enabled. Preserve each verified registration object and public key in an independent operator recovery archive with checksum and access audit. [Cloud KMS supports `EC_SIGN_ED25519`](https://docs.cloud.google.com/kms/docs/algorithms); [public-key retrieval requires an enabled version](https://docs.cloud.google.com/kms/docs/key-states), so historical verification must not depend on a later KMS fetch.

## Journal signatures and rotation

Each writer epoch uses a distinct Cloud KMS `ASYMMETRIC_SIGN` **CryptoKey** with one SOFTWARE `EC_SIGN_ED25519` version and a distinct writer service identity. Grant signing permission on that CryptoKey only, never on the key ring or project. [Cloud KMS IAM](https://docs.cloud.google.com/kms/docs/reference/permissions-and-roles) cannot independently scope versions of one CryptoKey. The writer has no key administration or destroy permission. Every slot and outcome envelope contains a canonical payload, the SHA-256 of its root-verified registration, and a KMS signature over `KAP2_JOURNAL_V1\0 || canonical(payload)`. The verifier selects the public key *only* through the root-verified registration map, validates signer epoch and partition/sequence/hash chain, and denies on missing, conflicting, unknown, or invalid signatures. [KMS asymmetricSign](https://docs.cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys.cryptoKeyVersions/asymmetricSign) accepts raw data for this algorithm and returns the exact version name; the runner checks that name and locally verifies the signature before publication.

Rotation requires a root-signed epoch `n+1` registration pointing to epoch `n`; a separate KMS CryptoKey and writer identity; a drained old write lane; and a unique conditional EPOCH slot signed by the new key. Initially the new identity has bucket read access only, with no signing or create grant. After revoking the old identity's old-key signing and bucket-create permissions, the runner uses a token issued **before** IAM cutover to attempt signing with both CryptoKeys and creating distinct journal objects. All must return 403 in three rounds **before** the operator grants new-key signing and bucket create to the new writer. The runner then checks new-writer bucket IAM and admits its write lane. A 403 samples permission propagation; it does not prove that earlier in-flight requests on other workers drained. A production barrier must separately inventory and join those requests. IAM cutover is distinct from cryptographic rotation: the new signed EPOCH object occurs only after old-token denial. Old public keys remain available for verification, while old private key versions can be disabled after cutover. Destruction timing must exceed the journal evidence and recovery policy; the [KMS destroy schedule](https://docs.cloud.google.com/kms/docs/destroy-restore) is not a substitute for archived public keys or independent witness retention. An emergency root rotation requires an out-of-band independently authenticated new pin, dual operator approval, and a blocked serving lane until the entire registration chain is revalidated.

## Restore and failure behavior

After any MariaDB restore, load the independent pinned root, discover and verify the full GCS registration and signed slot/outcome chains, and compare the latest committed witness sequence with the local partition fence before allowing disclosure. Database-restored keys, READY flags and grant rows provide no trust. Missing root pin, unavailable GCS, missing historic registration/public key, unknown signer epoch, signature mismatch, incomplete outcome, or local revision mismatch all deny and require operator recovery. Recover MariaDB only to a state reconciled with the witness; never backdate the witness to match the DB. Preserve the root pin and registration archive in recovery material with a separate access path from DB backups.

## Evidence boundary

Local synthetic tests verify that a self-signed attacker registration cannot replace the pinned root, that signed payload tampering fails, and that two registered epochs verify from the root and registration material without consulting database state. The runner requires two distinct CryptoKeys and writer identities plus a read-only verifier. It prepares a manual IAM cutover barrier and tests the pre-issued old token against both signing keys and journal create before admitting the new writer. It retains the 160 create-attempt, 5,000 object-request and 160 signing-request-per-key caps and uses synthetic partitions. **No live KMS/GCS signing, IAM propagation, in-flight drain, timeout, retention, rotation isolation, key recovery, or history latency has been run.**
