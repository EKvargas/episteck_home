# KAP-2 Home witness: isolated GCS probe provisioning proposal

**Pre-run proposal, updated 2026-10-08.** Erick subsequently authorized the isolated cloud probe and the open billing account. The actual provisioning, measurements and cleanup outcome are tracked in [live probe evidence](evidence/2026-10-08/LIVE_PROBE_EVIDENCE.md). PR #59 is accepted as a candidate for validation, not activation.

## Scope and location decision

Use a distinct Home-owned test project, proposed ID `episteck-home-kap2-probe`, subject to organization naming and billing approval. It must have no production grants or data. Compare two **regional Standard, flat-namespace** buckets using separate synthetic prefixes: `us-east4` (Northern Virginia, near the Ashburn Home host) and `europe-west3` (Frankfurt). Both are listed as available Cloud Storage regions in [Google's locations](https://docs.cloud.google.com/storage/docs/bucket-locations). The earlier Knowledge Frankfurt measurement does not select Home's region. First establish data-residency policy: if US storage is disallowed, do not provision the US bucket; record that the latency comparison cannot be performed and select only among eligible locations. Measure from the actual Home host, not this workstation.

Proposed names: `kap2-probe-home-us-east4-<random>` and `kap2-probe-home-europe-west3-<random>`, labels `kap2_probe=true`, `owner=home`, one prefix per run. Uniform bucket-level access, public access prevention, no versioning, no lifecycle rule, and **no retention policy or lock** during this phase. Retention behavior remains unproved. Production retention duration remains undecided until backup rollback horizon, detection and recovery bound are measured.

## Identities and privileges

Per region create **two writer service accounts** (old/new) and **two separate CryptoKeys**, one SOFTWARE `EC_SIGN_ED25519` key version each, in one regional key ring. Across two eligible regions the exact inventory is **one isolated project, two buckets, two key rings, four CryptoKeys, four active key versions, four writer accounts, one shared verifier account, and one project custom bucket role**; use an existing operator identity for setup, cutover and teardown. Initially the old writer has bucket `create/get/list` and `cloudkms.cryptoKeyVersions.useToSign` on **its own CryptoKey**; the new writer has bucket `get/list` only and no signing grant. After old-token denial, the operator grants new-writer bucket create and signing on the **new** CryptoKey. No writer gets a key ring/project signing grant or the other key's signing permission. The verifier receives bucket `get/list` and key-scoped public-key retrieval on both keys, never create/sign. The operator holds setup/teardown privileges outside serving code. Use short-lived impersonated tokens; no downloaded service-account keys. Preflight checks effective bucket permissions, including inherited grants. [Cloud KMS IAM](https://docs.cloud.google.com/kms/docs/reference/permissions-and-roles) does not independently scope key versions. [Cloud Storage IAM roles](https://docs.cloud.google.com/storage/docs/access-control/iam-roles) show why Object Admin is too broad and Object Creator lacks read/list.

The [signing trust candidate](SIGNING_TRUST_CANDIDATE.md) uses a separately pinned offline Ed25519 registration root. Prepare two root-signed registration JSON files offline for the chosen synthetic run ID and independently supply the trusted root PEM to the runner. Provision only after approval. The runner obtains an old-writer token before manual IAM cutover; the operator drains writers, revokes the old identity's old-key signing and bucket-create grants, and waits for propagation. Three rounds must return HTTP 403 for old-token signing against **both** keys and object creation. Only then does the operator grant new-writer create/sign and the runner check its bucket permissions before using it. These samples do not prove a distributed in-flight drain. No service-account private keys are created or downloaded.

## Budget and cleanup

Per region the runner caps **160 object-create attempts**, **5,000 total object create/GET/LIST requests**, and **160 KMS sign attempts per CryptoKey**, including denied cutover attempts. Two regions cap 320 creates, 10,000 object requests and 640 sign attempts. Objects are synthetic and under 1 KiB; at most 160 KiB per bucket. Run once per eligible region from the actual Ashburn Home host. A project budget alert of $5 is a notification, **not** a spending cap; manually stop on unexpected billing. At [regional Standard GCS prices](https://cloud.google.com/storage/pricing), treating all 10,000 requests as Class A at $0.005/1,000 gives $0.050. [KMS pricing](https://cloud.google.com/kms/pricing) lists SOFTWARE EC key versions at $0.000082192/hour and asymmetric cryptographic operations at $0.03/10,000: four versions held for 24 hours cost about $0.00789, and 640 sign attempts about $0.00192. Combined two-region request/key/sign estimate is **about $0.060 for one day**, plus storage, egress, IAM/API activity, retries, taxes and any billing minimum; it is not a hard billing ceiling. One region is approximately $0.030 on the same assumptions. Keep buckets no longer than one working day after evidence capture. Operator inventories objects and billing, removes synthetic objects, buckets, IAM bindings and accounts, disables test key versions, then closes the isolated project after archiving evidence and confirming no other work uses it. Key rings/CryptoKeys cannot be deleted like objects; disabled key versions may continue billing until destruction/project closure, and project/audit residue may persist. Do not schedule irreversible key destruction during this probe without separate authorization. No retention lock or policy is set.

## Required evidence before region or protocol approval

For each eligible region, run from Ashburn: real conditional slot/outcome create, concurrent writers, actual timeout-after-write and readback, pending outcome denial, corruption, takeover with old credential isolation, restore-before-revocation, pagination under concurrent append, and full-head verification at growing history sizes. Capture p50/p95/max latency, object request counts, error rates, and signing/verification after key rotation. Test unlocked retention behavior separately. The current local scanner and MariaDB/Frappe results do **not** prove live journal signature verification, network timeout recovery, GCS retention, or growing-history performance. Do not extrapolate GCS head latency to end-to-end Knowledge latency.
