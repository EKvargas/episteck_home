# KAP-2 Home witness: isolated GCS probe provisioning proposal

**Proposal only, updated 2026-10-08.** Erick's explicit authorization is required before any cloud probe provisioning. No project, bucket, identity, key, retention policy, or paid resource has been created. PR #59 is accepted as a candidate for validation, not activation.

## Scope and location decision

Use a distinct Home-owned test project, proposed ID `episteck-home-kap2-probe`, subject to organization naming and billing approval. It must have no production grants or data. Compare two **regional Standard, flat-namespace** buckets using separate synthetic prefixes: `us-east4` (Northern Virginia, near the Ashburn Home host) and `europe-west3` (Frankfurt). Both are listed as available Cloud Storage regions in [Google's locations](https://docs.cloud.google.com/storage/docs/bucket-locations). The earlier Knowledge Frankfurt measurement does not select Home's region. First establish data-residency policy: if US storage is disallowed, do not provision the US bucket; record that the latency comparison cannot be performed and select only among eligible locations. Measure from the actual Home host, not this workstation.

Proposed names: `kap2-probe-home-us-east4-<random>` and `kap2-probe-home-europe-west3-<random>`, labels `kap2_probe=true`, `owner=home`, one prefix per run. Uniform bucket-level access, public access prevention, no versioning, no lifecycle rule, and no retention lock during this phase. Set a short **unlocked** test retention policy only if a separate retention behavior test is approved; the baseline protocol probe should use no retention policy so teardown remains possible. Production retention duration remains undecided until backup rollback horizon, detection and recovery bound are measured.

## Identities and privileges

Create one probe writer service account per bucket/region, and a separate operator identity. The writer needs only bucket-scoped `storage.objects.create`, `storage.objects.get`, `storage.objects.list`; a custom role avoids the update/delete permissions in broad object roles. It must lack bucket administration, object update/delete, and retention permissions. A separate read-only verifier gets `storage.objects.get/list`. An operator with scoped project setup/teardown privileges creates and deletes test resources; that identity is unavailable to serving code. Use short-lived impersonated tokens; no downloaded service-account keys. Probe preflight checks effective permissions, including inherited grants. [Cloud Storage IAM roles](https://docs.cloud.google.com/storage/docs/access-control/iam-roles) show why Object Admin is too broad and why Object Creator alone lacks read/list.

The selected [signing trust candidate](SIGNING_TRUST_CANDIDATE.md) uses a separately pinned offline Ed25519 registration root and two Home-owned Cloud KMS `EC_SIGN_ED25519` signer versions for rotation testing. Provision a KMS key ring/key only in the isolated test project after authorization. Scope `cloudkms.cryptoKeyVersions.useToSign` to the probe writer on the two versions and `cloudkms.cryptoKeyVersions.viewPublicKey` to verifier/operator; no runtime identity gets KMS administration or key destruction. Prepare two root-signed registration JSON files offline for the chosen synthetic run ID and independently supply the trusted root PEM to the runner. A separate old/new writer identity and IAM cutover test remains required to prove takeover isolation; the current runner signs both epochs through one test identity and reports that limit. Do not create or download service-account private keys.

## Budget and cleanup

The runnable probe has hard caps of **160 object create attempts**, **5,000 combined object GET/LIST/create attempts**, and **160 KMS signing requests per version** per run, with synthetic objects under 1 KiB each. Run once per eligible region, with a project budget alert and a manual stop if the caps or unexpected billing are seen. On [current Cloud Storage pricing](https://cloud.google.com/storage/pricing), regional Standard flat namespace operations are $0.005 per 1,000 Class A (create/list) and $0.0004 per 1,000 Class B (get); even treating all 5,000 object requests as Class A gives an approximate **$0.025 object-operation ceiling per run**, before KMS key/storage/signing charges, request retry, network egress, IAM API charges, taxes or minimum billing. Under 160 KiB of Standard storage is much less than $0.01/month at the displayed per-GiB rate. This is an estimate, not a billing guarantee. Confirm KMS pricing and set a budget alert before any authorized provisioning. Keep buckets no longer than one working day after evidence capture. Operator inventories objects and billing, deletes the synthetic prefixes and buckets, removes IAM bindings/accounts, and closes the isolated project only after confirming no other work uses it. Cloud KMS key rings cannot be deleted; account for that durable test-project residue and close the isolated project only after evidence is archived. Do not lock retention during this probe; a locked policy would obstruct cleanup.

## Required evidence before region or protocol approval

For each eligible region, run from Ashburn: real conditional slot/outcome create, concurrent writers, actual timeout-after-write and readback, pending outcome denial, corruption, takeover with old credential isolation, restore-before-revocation, pagination under concurrent append, and full-head verification at growing history sizes. Capture p50/p95/max latency, object request counts, error rates, and signing/verification after key rotation. Test unlocked retention behavior separately. The current local scanner and MariaDB/Frappe results do **not** prove live journal signature verification, network timeout recovery, GCS retention, or growing-history performance. Do not extrapolate GCS head latency to end-to-end Knowledge latency.
